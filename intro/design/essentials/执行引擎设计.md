# 执行引擎 — 三节点循环

## 做了什么

LangGraph 内层的执行引擎由三个节点组成一个固定循环：

```
SopExecutionScheduler → ToolExecutor → ProgressUpdater → (循环回 Scheduler)
```

**Scheduler**（内层唯一的 LLM 节点）：读取带进度标记的 `sop_plan_steps`，定位当前未完成的步骤，生成工具调用（`TOOL_CALL: get_system_health(target='all')`），输出 `task_status` 决定循环走向。

**ToolExecutor**（纯代码）：接收 Scheduler 的工具调用，通过 `ToolDispatcher.dispatch()` 分发到对应工具函数，处理返回结果，将 `detail` 存入 VariableStore。

**ProgressUpdater**（纯代码）：将工具执行结果机械追加到 `sop_plan_steps` 的对应步骤行尾。支持四种追加模式——顺序步骤追加 `结果: 成功 | ...`、条件步骤追加 `因为...所以...`、失败步骤递增 `重试 N/M` 计数、未执行步骤自动标记 `已跳过（条件不满足）`。

**路由**（纯代码）：`graph/Builder.py` 中 `route_after_scheduler` 仅做一件事——检查 `task_status` 是否为 `"ONGOING"`，是则进入 ToolExecutor，否则（FINISH/ERROR/INTERRUPT）结束图执行。

## 为什么这么做

最关键的设计决策：**ProgressUpdater 不用 LLM**。

v1 曾用 LLM（ProgressSummarizer）做进度更新，结果是：LLM 创造性改写步骤文本（改变原有语义）；格式不一致（同样的"完成"有时写"已完成"有时写"执行完毕"）；额外消耗 12-25 秒推理时间；可能遗漏步骤或错误标记。进度更新的本质是机械的字符串拼接——知道目标步骤编号、知道步骤类型、知道执行结果，就能用确定性规则拼出进度标记。用 Python 做这件事零延迟、零幻觉、格式绝对一致。

路由同样不能让 LLM 决定。如果 LLM 决定"下一步去哪"，那它可能在 ONGOING 和 FINISH 之间反复横跳，或者意外进入死循环。把路由硬编码为字符串比对，确保图的行为在编译时就是确定的。

## 不这么做会怎样

保留 v1 的 LLM 进度更新 → 每轮多 12-25 秒延迟，6 步 SOP 额外增加 1-2 分钟；步骤文本被 LLM 改写后，Scheduler 在下一轮可能"读不懂"自己上一步做了什么。LLM 控制路由 → 行为不可预测，同一条 SOP 每次执行的退出时机可能不同。
