# 关键设计概述

CutinAgent 的 8 大关键设计要点，对应 `CLAUDE.md` 第 3 节。每个要点的完整论述见对应的设计文档。

---

## 3.1 Thinker + Formatter — 双阶段推理与格式防幻觉

所有 LLM 节点统一采用双阶段推理：
- **Thinker** (temperature 0.4): 自由文本推理链，无格式约束
- **Formatter** (temperature 0.0): 从推理链提取结构化输出，由 validator 做格式校验：
  - `SopExecutionSchedulerValidator`: 校验 TOOL_CALL `Tool_ID(args)` 格式 + 调度器三元组
  - `UserCoordinatorValidator`: 校验 SOP_ID 防幻觉 + 五字段规则（SOP 匹配由 UserCoordinator 完成）
- 校验失败 → 错误信息追加到 prompt → Formatter 重试（最多 3 次）

> 详见：[ThinkerFormatter设计.md](ThinkerFormatter设计.md)

## 3.2 UserCoordinator — 人机协作网关

**意图分类**：每轮将用户消息分为 CHAT / UNCERTAIN / EXECUTE 三类，存疑时优先归为 CHAT 或 UNCERTAIN。
同时负责扫描 SOP_LIBRARY 匹配用户需求，输出 `SOP_ID`（v2 重构后合并了原 InitialSOPRetriever 的职责）。

**三级渐进式确认（EXECUTE 专属）**，跨越多轮对话，由 CURRENT_DIALOGUE 追踪阶段：
- Stage 1 (SOP 匹配)：推荐 SOP → 请求确认。IS_EXECUTE=false, SOP_ID 填充
- Stage 2 (行动细化)：确定缺失信息（时间、目录等），提供默认值。IS_EXECUTE=false, SOP_ID + CURRENT_ACTION 填充
- Stage 3 (最终确认)：输出 LONG_TERM_INTENT。IS_EXECUTE=true, 五字段全部填充

**IS_EXECUTE 总闸**：
- `"false"` → 渐进式确认模式，LONG_TERM_INTENT 必须为 NONE（Validator 强制）
- `"true"` → 最终确认模式，展示摘要等待用户 y/n；y → 加载 SOP → 执行图；LONG_TERM_INTENT 必须非 NONE

**五字段输出**：CHAT_MESSAGE（始终非空）, SOP_ID, CURRENT_ACTION, LONG_TERM_INTENT（仅 IS_EXECUTE=true 时有效）, IS_EXECUTE

**反幻觉设计**：Thinker 正面引导"基于已有 SOP_LIBRARY 描述能力"，而非打补丁式约束"不要编造"。每个意图分支显式要求 `Output CHAT_MESSAGE`。Formatter 不做创造性工作（temp 0.0）。Validator 做 SOP_ID 白名单校验。

> 详见：[UserCoordinator设计.md](UserCoordinator设计.md)

## 3.3 Compactor — 执行评价与历史压缩

每次 SOP 执行完毕后运行，输出三字段：
- **EVALUATION**：1-2句，SOP 是否达成 CURRENT_ACTION 目标
- **CONVERSATION_SUMMARY**：2-4句对话摘要 → 追加到 CONVERSATION_HISTORY
- **EXECUTION_SUMMARY**：2-4句执行摘要 → 追加到 EXECUTION_HISTORY

**对话生命周期**：
- CURRENT_DIALOGUE 每轮追加 User/Agent 消息，仅在 Compactor 完成 + 用户满意后清除
- CONVERSATION_HISTORY / EXECUTION_HISTORY 累计追加，实现跨 SOP 周期的长期记忆

> 详见：[Compactor设计.md](Compactor设计.md)

## 3.4 SOP 存储与校验

- **CSV 索引** (`sop/sops.csv`): SOP_ID, Objective, Description, Keywords — 由 `build_sop_library_index()` 构造为 `SOP_LIBRARY` 文本，UserCoordinator 用其做快速匹配
- **Markdown 全文** (`sop/{SOP_ID}.md`): UserCoordinator 匹配成功后，main.py 调用 `load_sop_markdown()` 加载并校验 7 个标准 section
- **加载时校验**: `SopSpecChecker` 对 Plan_Steps 执行 13 项 DSL 规则校验（详见 `sop编写规范.md`），Retry_Limit 必须为 ≥1 的正整数。校验失败直接拒绝加载
- **异常处理**: SOP 中 `Global_Exception_Handling` section 定义全局异常条件，Scheduler 每轮扫描并匹配
- `NO_MATCHING_SOP`: 无法匹配时系统直接终止

> 详见：[SOP体系设计.md](SOP体系设计.md)

## 3.5 工具合约与变量传递

所有工具必须返回四字段 dict：
- `status`: `"成功"` 或 `"失败"`
- `conclusion`: 单句结论或失败原因
- `summary`: 可选的精简数据摘要
- `detail`: 可选的结构化详细数据

`detail` 非空 → ToolExecutor 自动存入 `VariableStore`，生成变量名 `VAR_{TOOL_ID}`。后续步骤通过 `data=VAR_{TOOL_ID}` 引用，ToolDispatcher 运行时从 VariableStore 解析为实际数据。工具内部完成"采集-分析-判断"，严禁把 raw data 抛给 4B 模型。

> 详见：[工具合约设计.md](工具合约设计.md)

## 3.6 进度更新与重试

- **ProgressUpdater** (纯代码，不调 LLM): 根据步骤类型将工具执行结果追加到 SOP_PLAN 行尾，支持 4 种追加模式（顺序/条件/并行/重试）+ 跳过间隙填充
- **重试机制**: Scheduler (LLM) 根据执行结果决定是否重试及调整参数；ProgressUpdater (纯代码) 检测已有 `结果:` 标记后自动递增 `重试 N/M` 计数；达到 `Retry_Limit` 硬上限时追加 `已达到重试上限` 标记，不再允许重试

> 详见：[进度更新与重试设计.md](进度更新与重试设计.md)

## 3.7 日志系统

- `debug_logger.py`: 每节点每轮记录 Thinker 输入/推理链/Formatter 重试日志/最终结果/耗时/token 用量 → `history/{ts}_{slug}/round_N/{NodeName}.txt`
- `log_state_snapshot()`: 每节点执行后输出 OverallState 全量快照为 JSON → `history/{ts}_{slug}/round_N/state_{node_name}.json`，完整审计追踪

> 详见：[日志系统设计.md](日志系统设计.md)

## 3.8 图结构与路由

路由硬编码，非 LLM 决策：

| 条件 | 动作 |
|------|------|
| `task_status == "ONGOING"` | → ToolExecutor → ProgressUpdater → 循环回 Scheduler |
| FINISH / ERROR / INTERRUPT | → END |

```
[entry] → [SOP Execution Scheduler] --FINISH/ERROR/INTERRUPT--> END
                | (ONGOING)
                v
        [ToolExecutor] → [ProgressUpdater] → (循环回 Scheduler)
```

> **v2 重构**：InitialSOPRetriever 已从图中移除。SOP 匹配由 REPL 外层的 UserCoordinator 完成，SOP 加载由 main.py 直接调用 `load_sop_markdown()`。图入口点直接是 SOP Execution Scheduler。

REPL 外层路由（main.py）：

| 条件 | 动作 |
|------|------|
| `is_execute == "false"` | 显示 CHAT_MESSAGE → 继续 REPL 循环 |
| `is_execute == "true"` + 用户确认 y | 加载 SOP → 运行执行图 → Compactor |
| `is_execute == "true"` + 用户拒绝 | 重新进入 UserCoordinator |

> 详见：[图结构与路由设计.md](图结构与路由设计.md)
