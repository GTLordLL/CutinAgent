# 图结构与路由 — LangGraph 执行层的拓扑与状态管理

## 做了什么

CutinAgent 的 SOP 执行内层由 LangGraph `StateGraph` 构建，包含 3 个节点和硬编码条件路由。SOP 匹配与加载在 REPL 外层（UserCoordinator + `load_sop_markdown()`）完成，图入口直接是 `sop_execution_scheduler`。

### 图拓扑：3 节点循环

`graph/Builder.py` 的 `build_graph(resources)` 创建 `StateGraph(OverallState)`，添加三个节点：`sop_execution_scheduler`（LLM 节点）、`tool_executor`（纯代码数据节点）、`progress_updater`（纯代码数据节点）。

入口点为 `sop_execution_scheduler`。一条条件边从 scheduler 出发，通过 `route_after_scheduler` 函数决定走 `tool_executor` 还是 END。两条固定边：`tool_executor → progress_updater` 和 `progress_updater → sop_execution_scheduler`。编译后返回可执行图实例。

```
               ┌──────────────────────────────────┐
               │                                  │
               ▼                                  │
[sop_execution_scheduler] ──(ONGOING)──► [tool_executor]
        │                                      │
        │ (FINISH/ERROR/INTERRUPT)             │
        ▼                                      ▼
       END                              [progress_updater]
                                               │
                                               │ (无条件)
                                               │
                                               └──────────────────┘
```

### 条件路由：route_after_scheduler

`graph/Builder.py` 的 `route_after_scheduler(state)` 是 Scheduler 后唯一的条件路由函数。它读取 `state.get("task_status", "ONGOING")`：如果是 `"ONGOING"` 则返回 `"tool_executor"` 进入执行循环，其他值（FINISH/ERROR/INTERRUPT）返回 END 终止图。

`task_status` 由 Scheduler Formatter 输出，由 `SopExecutionSchedulerValidator` 校验仅允许四个值：`FINISH`、`ONGOING`、`ERROR`、`INTERRUPT`。默认值 `"ONGOING"` 是一个安全选择——如果 `task_status` 意外缺失，图不会错误地终止。

路由是**字符串比对**（`== "ONGOING"`），不是 LLM 决策。LLM 只能通过 `task_status` 字段影响路由（它输出的值），而路由本身的逻辑是代码控制的——确定性的、可预测的、零延迟的。

### 边的设计理由

三条边各有不同的路由语义：

| 边 | 类型 | 语义 |
|----|------|------|
| `sop_execution_scheduler → tool_executor` | 条件 | 只有 Scheduler 输出 ONGOING 时才需要执行工具 |
| `tool_executor → progress_updater` | 固定 | 每次工具执行后必须更新进度 |
| `progress_updater → sop_execution_scheduler` | 固定 | **无条件**回到 Scheduler，由 Scheduler 判断下一步 |

第三条边是最关键的：ProgressUpdater 之后**总是**回到 Scheduler，即使 `task_status` 是 ERROR 或 INTERRUPT。这是有意为之——Scheduler 在下一轮被调用时，可以检查异常条件并匹配 `Global_Exception_Handling` 中的规则。

### 终止机制

图不会直接从 ProgressUpdater 终止。终止路径始终是：ProgressUpdater → Scheduler → route_after_scheduler → END。这意味着每个终止状态（FINISH、ERROR、INTERRUPT）都会多调用一次 Scheduler。这次"额外"调用的作用是让 Scheduler 在输出终端状态前检查：是否有全球异常条件被触发、是否应该 INTERRUPT 等待人工介入、是否所有步骤都已完成（确认 FINISH 之前没有遗漏条件步骤）。

### v2 入口：直接从 Scheduler 开始

v1 的图入口是 InitialSOPRetriever（LLM 节点，从用户输入匹配 SOP）。v2 中 SOP 匹配已移到 REPL 外层：`main.py` 在调用图之前已经完成 SOP 匹配和加载——UserCoordinator 输出 `matched_sop_id` → `load_sop_markdown()` → 将 Plan_Steps 等字段写入 state → 图以完整的 SOP 状态开始执行。

### OverallState：37 字段 TypedDict

`graph/OverallState.py` 定义了 `OverallState`（`TypedDict`），包含 37 个字段，分为 10 个语义组：

| 组 | 字段数 | 示例字段 |
|----|--------|---------|
| 用户输入 + 会话 | 5 | `user_instruction`, `session_dir`, `session_id`, `session_name`, `sop_ids` |
| SOP 匹配结果 | 5 | `matched_sop_id`, `sop_plan_steps`, `sop_objective`, `sop_tools_required`, `sop_exception_handling` |
| 工具调用 | 5 | `current_tool_call`, `current_tool_args`, `current_tool_calls`, `current_tool_call_raw`, `execution_result` |
| 工具执行结果 | 3 | `tool_status`, `tool_summary`, `tool_detail_var` |
| 进度追踪 | 2 | `last_step`, `task_status` |
| 重试 + 循环控制 | 2 | `retry_limit`, `current_round` |
| 最终输出 | 1 | `final_report` |
| REPL 状态（UserCoordinator 输出） | 7 | `chat_message`, `is_execute`, `current_dialogue`, `current_action`, `long_term_intent`, `conversation_history`, `execution_history` |
| Compactor 输出 | 3 | `compactor_evaluation`, `compactor_conversation_summary`, `compactor_execution_summary` |
| ChatCompactor | 3 | `thinker_input_tokens`, `chat_compact_requirement`, `chat_conversation_summary` |

### 并行调用兼容

`current_tool_calls` 是一个列表（由 Scheduler 的 `_parse_multiple_tool_calls()` 从 `|` 分隔的 TOOL_CALL 解析），`current_tool_call` + `current_tool_args` 提供标量回退。ToolExecutor 检查 `current_tool_calls` 是否存在且非空来决定走并行还是单调用路径。这允许 Scheduler 输出单工具调用或多工具调用（`|` 分隔）——ToolExecutor 自动适配。

### 图执行封装：run_sop_graph()

`repl/sop_runner.py` 的 `run_sop_graph(app, state)` 封装了 LangGraph 的 `app.stream(state, stream_mode="updates")` 事件循环：收集每个节点的耗时、聚合 `task_status`（状态可能经历 ONGOING → FINISH 的变化）、追踪 `current_round` 最大值、节点输出通过 `state.update(output)` 累积、打印到终端 + 记录到调试日志。

## 为什么这么做

### 路由硬编码而非 LLM 决策

这是 v2 最关键的图设计决策。v1 曾尝试让 LLM 节点输出路由决策（类似于"下一步去 ToolExecutor"还是"去 END"）。结果：LLM 有时在 ONGOING 和 FINISH 之间输出不一致（同一轮说 ONGOING 下一轮说 END 然后又说 ONGOING），导致不可预测的行为。

`route_after_scheduler` 做的是**字符串比对**——`task_status == "ONGOING"`。这是确定性的、可预测的、零延迟的。LLM 只能通过 `task_status` 字段影响路由（它输出的值），而路由本身的逻辑是代码控制的。

### ProgressUpdater 始终回 Scheduler 的理由

在 ProgressUpdater 之后不做条件路由（直接到 END 或回到 Scheduler），而是**无条件**回到 Scheduler，再由 Scheduler 通过 `route_after_scheduler` 决定。这确保了：

1. **异常检查**：如果 ProgressUpdater 标记了重试上限，Scheduler 下一轮可以检测到并输出 ERROR 或 INTERRUPT——如果 ProgressUpdater 后直接 END，重试上限标记被追加了但没有人处理
2. **全局异常匹配**：Scheduler 每轮检查 `Global_Exception_Handling` 中的条件是否匹配——如果某个条件突然变为真（如"磁盘空间在执行期间下降到 5% 以下"），Scheduler 可以输出 INTERRUPT 暂停执行
3. **状态一致性**：始终由 Scheduler 决定"下一步做什么"——路由语义清晰、责任单一

代价是每次终止都多一次 Scheduler 调用（增加约 15-25 秒延迟）。但对于 6 步 SOP 总共约 2-3 分钟的执行时间，1 次额外调用的开销是可以接受的。确定性优于延迟优化。

### v2 入口直接在 Scheduler 的理由

v1 的 InitialSOPRetriever 在图内做 SOP 匹配——它需要从用户消息中选择 SOP_ID，加载 SOP，然后启动执行。问题：图内 SOP 匹配无法做渐进式确认（用户没有机会审查匹配结果），且 InitialSOPRetriever 是 LLM 节点，匹配可能错误但图一旦启动就无法回调。

v2 将匹配移到 REPL 外层 UserCoordinator——SOP 匹配和确认在执行前完成。图只负责"执行已确认的 SOP"——职责更窄、更可靠。

### 图执行封装隔离复杂度

`run_sop_graph()` 将 LangGraph stream 事件循环、状态累积、节点计时、终端打印、错误处理封装在一起。`main.py` 只需要调用 `run_sop_graph(app, state)` 并拿到最终状态——不关心 LangGraph 内部如何实现流式。

### 字符串比对 vs 枚举

`task_status` 被存为字符串（`"ONGOING"` / `"FINISH"` 等）而非 Python 枚举。这不是偷懒——LangGraph state 在序列化/反序列化过程中通过 JSON，而 JSON 不知道 Python 枚举。字符串在 JSON 边界之间始终保持其值。如果使用枚举，state JSON 快照会包含不可反序列化的枚举引用或丢失类型信息。

## 不这么做会怎样

### LLM 控制路由

Scheduler 说 "TASK_STATUS: ONGOING" → 下一轮说 "TASK_STATUS: FINISH" → 再下一轮说 "TASK_STATUS: ONGOING"（模型不一致）。图在循环中进出，用户看到任务"在完成和进行中之间反复跳跃"。字符串比对 `== "ONGOING"` 消除了这种不确定性——Scheduler 的输出是概率的，但路由对该输出的解释是确定性的。

### ProgressUpdater 后直接 END

某个 SOP 步骤在第三次重试后失败。ProgressUpdater 标记了重试上限——但图直接结束了。没有机会处理这个失败状态（是否应该 INTERRUPT 等人工介入？是否应该继续后续步骤？）。信息被记录下来但没有被消费。

### 图中有 SOP 匹配节点（v1 模式）

用户说"检查系统"，模型匹配 `FULL_SYSTEM_HEALTH_CHECK` → 开始执行。但用户实际想说的是"检查 git 提交记录"（不够清晰）。图已经开始执行了，用户无法中断匹配。SOP 匹配和执行之间缺少人机确认环节——这正是 v2 把匹配移到 REPL 外层的动机。

### 无图级最大轮次守卫

当前实现没有硬性 `max_rounds` 上限。如果 Scheduler 持续输出 ONGOING，图将无限循环（LLM 调用无限进行）。这是一个已知的限制，在实际运行中依赖 4B 模型在 6 轮内自然收敛到 FINISH。对于生产环境，应在 `run_sop_graph()` 中添加 `max_rounds` 检查作为熔断器。

### state 缺少 TypedDict 定义

如果 state 是一个普通 dict 无类型定义，节点代码中对 state 字段的 typo 会在运行时静默返回 None → 然后进入路由分支。TypedDict 不提供运行时检查，但它提供 IDE 支持和类型标注——减少因 state 字段名拼写错误导致的 bug。
