# 工具合约 — 四字段契约与变量传递

## 做了什么

CutinAgent 的 11 个工具全部遵循统一的四字段返回契约：

```python
{"status": "成功|失败", "conclusion": "结论/原因", "summary": "精简摘要", "detail": "详细数据"}
```

ToolExecutor 通过 `fields.get("status", "")` 统一解析，字段缺失不会导致崩溃。ToolDispatcher 用 Python 字典做路由（`toolbox[tool_id](**args)`），不涉及 LLM。

**工具内部闭环**：每个工具内部完成"采集 → 分析 → 判断"全流程。例如 `get_system_health` 调用 `psutil` 采集 CPU/内存/磁盘数据 → 与阈值比对（CPU 80%、内存 90%、磁盘 85%）→ 返回 `成功 | CPU 2.9%（正常）| 内存 70.4%（正常）| 磁盘 41.6%（正常）`。4B 模型收到的不是 raw data，而是已经过判断的结论文本。

**变量传递**：`detail` 非空时，ToolExecutor 自动调用 `VariableStore.store(detail, tool_id)`，生成变量名 `VAR_{tool_id}`。后续 Scheduler 在工具调用中引用 `data=VAR_get_system_health`，ToolDispatcher 在运行时从 VariableStore 解析为实际数据。同一工具被多次调用时自动追加序号（`VAR_get_system_health_2`），重试不会覆盖。

**安全设计**：所有 11 个工具均为只读命令（`ps`、`df`、`ss`、`grep` 等），无写入/删除/修改操作。最坏情况：4B 模型幻觉导致错误诊断，而不是删除你的文件。

## 为什么这么做

统一契约是"加工具不改框架"的前提。新工具只要返回四字段 dict，ToolExecutor 就不需要任何修改——它只和契约打交道，不关心具体工具的实现。没有统一契约的话，每个工具都需要在 ToolExecutor 中写专门的解析逻辑，加一个工具要改两处代码。

"采集-分析-判断"闭环是适配 4B 模型的关键设计。4B 模型上下文仅 8K tokens，如果把 `ps aux` 的 200 行 raw output 直接塞给模型，不仅浪费上下文，模型还可能错误解读数据。工具在 Python 层面完成阈值比对和状态判断，模型只收到"CPU 正常"这个结论——认知负担从 LLM 转移到了确定性代码。

## 不这么做会怎样

每个工具返回不同格式 → ToolExecutor 逐工具 if-else 解析 → 加工具 = 改 ToolExecutor → 框架不闭合。工具返回 raw data → 两轮后 8K 上下文塞满 → 模型截断 → 后续步骤丢失关键信息。工具包含写入操作 → 模型幻觉可能造成不可逆的破坏。
