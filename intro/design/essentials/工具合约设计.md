# 工具合约 — 四字段契约与变量传递

## 做了什么

CutinAgent 的所有工具遵循统一的四字段返回契约，由 ToolExecutor 统一处理、ToolDispatcher 字典路由、VariableStore 管理变量传递。

### 四字段统一契约

每个工具函数返回如下 dict：

| 字段 | 含义 | 用途 |
|------|------|------|
| `status` | `"成功"` 或 `"失败"` | Scheduler 判断是否需要重试 / ProgressUpdater 格式化 |
| `conclusion` | 单句结论或失败原因 | 追加到进度标记、展示给用户 |
| `summary` | 可选的精简数据摘要 | 同上 |
| `detail` | 可选的结构化详细数据 | 存入 VariableStore，供后续步骤通过 `VAR_` 引用 |

### ToolExecutor 统一处理

`data_nodes/ToolExecutor.py` 的 `tool_executor_node(state)` 是 LangGraph 纯代码数据节点，不调 LLM。它接收 Scheduler 输出的工具调用，通过 ToolDispatcher 执行，再统一处理返回结果。

**并行/单调用兼容**：`current_tool_calls` 是列表时走并行模式（顺序遍历，结果按 `|` 聚合），否则走单调用模式。`current_tool_call` + `current_tool_args` 提供标量回退，保证向后兼容。

**四字段处理**（`_process_tool_result`）：从工具返回的 dict 中提取四个字段，使用 `.get()` 带默认值——字段缺失或拼写错误不会导致崩溃。`detail` 非空时调用 `VariableStore.store()` 存入变量并获取变量名。最后将完整输出写入 JSON 文件持久化。

### ToolDispatcher 字典路由

`tools/ToolDispatcher.py` 的 `dispatch(tool_id, args)` 用 Python 字典（`self.toolbox`）做工具查找和调用。字典查找是 O(1)，无 LLM 参与。

三层异常保护：
1. 未知工具 ID → 返回 `{"status": "失败", "conclusion": "未知工具: ..."}` 而非 KeyError
2. `TypeError`（参数不匹配）→ 单独捕获，错误信息更精确（如 "缺少参数 target"）
3. 通用 `Exception` → 兜底捕获，确保任何工具故障都转化为统一格式的失败返回

运行时自动解析 `VAR_` 前缀的参数引用：遍历所有参数值，若字符串以 `VAR_` 开头则从 VariableStore 解析为实际数据。

### VariableStore：模块级字典存储

`data_nodes/VariableStore.py` 使用模块级 `_store: dict[str, str]` 作为变量存储，所有导入共享同一实例。变量名格式为 `VAR_{tool_id}`。同一工具的多次调用会产生自动递增的序号（`VAR_get_git_diff`、`VAR_get_git_diff_2`、`VAR_get_git_diff_3`），重试不覆盖之前的值。`resolve()` 从 store 中取值，不存在时返回空字符串。

### VAR_ 变量引用

Scheduler 在工具调用中使用 `data=VAR_get_git_diff` 引用之前存储的变量。ToolDispatcher 在运行时通过 `resolve()` 将 `VAR_` 前缀的引用解析为实际存储的数据，再传入工具函数。

### 工具内部："采集-分析-判断"闭环

每个工具在 Python 层面完成"采集 → 分析 → 判断"全流程，返回的是**结论文本**而非原始数据。以 `get_system_health` 为例：采集（`psutil.cpu_percent()`、`psutil.virtual_memory()`、`psutil.disk_usage()`）→ 分析（与阈值比对：CPU 80%、内存 90%、磁盘 85%）→ 判断（返回 `成功 | CPU 2.9%（正常）| 内存 70.4%（正常）| 磁盘 41.6%（正常）`）。

4B 模型收到的 `conclusion` 是已分析好的结论文本，而非数十个原始指标数值。

### 工具输出持久化

每次工具执行后，完整输出保存为 `history/{round_N}/tool_{tool_id}.json`，包含四字段完整值加可选的执行耗时。

### 安全：全部只读操作

当前注册的 11 个工具全部为只读：`ps`、`df`、`ss`、`grep`、`cat`、`ping` 等诊断命令，以及 `git status/diff/log` 等查询操作。最坏情况：4B 模型幻觉导致错误诊断——而非删除文件或破坏系统配置。

---

## 为什么这么做

### 统一契约 = 加工具不改框架

新工具只要返回四字段 dict，ToolExecutor 的 `_process_tool_result()` 处理它无需修改。`fields.get("status", "")` 不关心工具内部实现。加一个工具只需：写 Python 函数 → 在 `tools.csv` 注册一行。ToolExecutor、ProgressUpdater、VariableStore——全部没有改动。

如果每个工具返回不同格式（一个返回 `{success: True}`，另一个返回 `{error: None}`，再一个返回纯字符串），ToolExecutor 需要为每个工具写 if-else 解析逻辑。加工具 = 改 ToolExecutor = 框架不闭合。

### "采集-分析-判断"闭环是适配 4B 模型的核心

4B 模型仅 8K 上下文窗口，处理能力有限。如果把 `ps aux` 的 200 行 raw output 直接塞给模型：浪费上下文（200 行 raw data 占用约 1000+ tokens），模型可能错误解读数据（4B 模型数值推理能力有限），模型需要额外的"分析"步骤变为额外的 LLM 调用。

让 Python 做阈值比对、状态判断、数据格式化——这些是确定性计算，代码比 LLM 更可靠且零延迟。模型收到的结论文本已经是"分析后"的，可以立即用于下一步的决策。

### 字典路由而非 LLM 路由

工具选择（Scheduler Thinker 决定调用哪个工具）和工具分发（ToolDispatcher 执行调用）是分离的。工具选择需要智能（LLM），工具分发需要快和可靠（Python 字典查找）。

如果 LLM 同时做选择和分发 → LLM 可能"调用"不存在的函数 → 运行时报错。如果代码做选择 → 代码需要理解 SOP 上下文和步骤目标 → 代码做不到。分离后各司其职。

### VAR_ 变量传递让步骤间数据流动不依赖模型记忆

SOP 的步骤 1 产出数据（如文件 diff），步骤 3 需要消费它。没有变量传递的话：要么依赖 4B 模型"记住"步骤 1 的输出（8K 上下文 + 多轮后记忆不可靠），要么所有数据通过 state 显式传递（state 字段膨胀）。

VAR_ 引用让数据在 Python 内存中保持精确，模型只需要知道"引用 `VAR_get_git_diff`"这个符号名——对模型是低认知负荷。

### 异常分层处理

ToolDispatcher 的三层异常处理（未知 ID → 失败，TypeError → 失败，通用 Exception → 失败）确保任何工具故障都转化为统一格式的 `{"status": "失败", ...}` 返回而非异常传播。执行图不会因一次工具调用失败而崩溃——ProgressUpdater 标记失败状态，Scheduler 下一轮根据失败状态决定重试或终止。

## 不这么做会怎样

### 工具各自不同的返回格式

`tool_A` 返回 `{"ok": True, "data": ...}`，`tool_B` 返回 `{"status": "OK", "message": ...}`，`tool_C` 返回 `"success"` 字符串。ToolExecutor 需要一个巨大的 if-elif-else 分支来解析每个工具的返回值。加工具 = 修改 ToolExecutor = 框架不闭合 = 维护成本无限增长。

### 工具返回 raw data

`check_network_port` 返回 `ss -tlnp` 的完整输出（50 行）→ 塞给 4B 模型 → 模型需要自己判断端口状态。两轮后上下文用掉 50%，Scheduler 丢失了前几步的进度标记 → 后续步骤质量下降。工具内部做判断，模型收到 `"端口 8080 已监听（nginx），端口 3000 未开放"`——认知负担从 LLM 转移到确定性代码。

### LLM 做工具路由

假设 dispatcher 不存在，Scheduler 直接调用 Python 函数。LLM 输出 `call sys_diagnostic()` —— 这不是注册过的函数名。运行时 `AttributeError`。或者 LLM 调用一个不存在的写操作——造成不可逆的后果。

### 无变量传递机制

步骤 1：`get_git_diff()` 返回 200 行 diff → 步骤 3：`generate_commit_message` 需要这个 diff 作为输入。没有 VAR_ 传递的话，要么把 200 行 diff 完整写回 state → 放入 Formatter prompt（token 爆炸），要么依赖 Scheduler Thinker "记住" diff（4B 模型多轮后记不准确）。

### 只读操作是审慎设计而非限制

如果工具集中有写入/删除操作，4B 模型的幻觉可能产生不可逆的后果。当前的工具集覆盖了 Git 操作 + Linux 诊断——这些是个人开发者最常见的使用场景。工具集可以扩展，但每新增一个写操作工具都需要仔细考虑安全影响。
