# 进度更新与重试 — 纯代码驱动的 SOP 步骤追踪

## 做了什么

ProgressUpdater 是 LangGraph 执行循环中的第三个节点，用**纯 Python 代码**将工具执行结果追加到 SOP Plan_Steps 文本的对应步骤行尾。不调 LLM。这是 v2 的核心架构变更之一——v1 使用 LLM（ProgressSummarizer）做进度更新，v2 用机械字符串操作替代。

### 输入与输出

`data_nodes/ProgressUpdater.py` 的 `progress_updater_node(state)` 从 state 读取 7 个字段：`sop_plan_steps`（当前带进度标记的 Plan_Steps 文本）、`last_step`（Scheduler 输出的 NEXT_STEP，如 `"3. 调用 get_system_health(...)"`）、`current_tool_call_raw`（刚被执行的工具调用字符串）、`tool_status`（成功/失败）、`tool_conclusion`（结论/原因）、`tool_summary`（精简数据）、`tool_detail_var`（VariableStore 变量名，可为空）、`retry_limit`（SOP 全局重试上限）。输出 2 个字段：更新后的 `sop_plan_steps` 和递增后的 `current_round`。

### 步骤定位

从 `last_step` 字符串提取步骤编号：用正则匹配行首的数字部分。然后调用 `parsers/sop_plan.py` 的 `_parse_steps()` 按 `N. ` 分割 Plan_Steps 文本为步骤列表，按编号查找目标步骤。无法解析步骤编号时静默返回（不更新 plan）——这是一个安全的入口保护，last_step 格式异常不会导致崩溃。

### 跳过间隙填充

在更新目标步骤之前，先检查上一个已标记步骤和目标步骤之间是否有跳过的步骤（条件分支不满足）。`_fill_skipped_gaps()` 将中间所有未标记步骤追加 `已跳过（条件不满足）。`。

`_is_step_marked()` 检查步骤是否已有任何状态标记（`结果:` / `已跳过` / `重试` / `已达到重试上限`）——四种标记中任意一个都算"已标记"。

### 四种更新模式

更新前先通过 `_classify_step()` 分类步骤类型，通过 `_already_has_result()` 检查是否为重试（已有 `结果:` 标记）。然后根据组合走不同分支：

#### 模式 1：顺序/并行更新（`_update_sequential`）

清除可能的旧跳过标记，然后拼接固定格式的结果文本：`结果: {status} | {conclusion} | {summary}。`。清除子行。输出示例：`1. 调用 get_system_health(target='all') 结果: 成功 | 系统正常 | CPU 2.9% 内存 70.4%。`

#### 模式 2：条件步骤更新（`_update_conditional`）

从步骤文本中用正则 `如果(.+?)，就\s*调用\s*(\w+)\(` 解析出条件分支列表。匹配 `tool_call_raw` 中实际调用的工具 ID 来确定走了哪个分支。最终输出 `因为{条件}，所以调用... 结果: ...。`——保留了条件的因果链。

#### 模式 3：重试更新（`_update_with_retry`）

核心机制是剥离-重建策略：

1. 用 `_extract_retry_count()` 从 header 正则提取当前重试次数
2. **完全剥离**旧的 `结果:`、`重试 N/M`、`已达到重试上限`、`已跳过` 标记——还原干净的步骤基础文本
3. 递增重试计数并检查是否超过 `retry_limit`
4. 追加新的结果 + 重试计数（如 `重试 2/3`）或 `已达到重试上限（3次），当前步骤不允许再次重试。`

剥离-重建避免了标记堆叠：如果不清除旧标记，3 次重试后步骤行尾会堆积 3 个 `结果:` 和 3 个 `重试 N/M`，文本膨胀且难以解析。

#### 模式 4：跳过间隙填充

FINISH / INTERRUPT / ERROR 类型的步骤不处理——它们不是可执行步骤，不需要进度标记。

### 结果格式化

`_format_result()` 按状态分支格式化：失败时省略 summary（失败状态下的 summary 通常无意义），成功时拼接 status + conclusion + summary 三字段。detail_var 非空时追加 `[变量: VAR_xxx]` 引用。

### ProgressUpdater 自身日志

`_log_progress_update()` 写入 `round_{N}/ProgressUpdater.txt`，包含 target_step、step_type、is_retry、gaps_filled、elapsed 以及更新前后的完整 Plan_Steps 对比——对排查条件分支和重试逻辑的问题至关重要。

## 为什么这么做

### v1 的 LLM 进度更新失败模式

v1 的 ProgressSummarizer（LLM 节点）存在三个根本问题：

1. **创造性改写**：LLM 被要求"将执行结果追加到步骤行尾"，但它偶尔会改写步骤文本本身——改变原有语义。例如原步骤 `"检查 CPU、内存、磁盘使用率"` 被改写成 `"已完成系统资源检查"`——丢失了原始的"检查什么"信息
2. **格式不一致**：同样的成功状态有时写 `"已完成"`，有时 `"执行完毕"`，有时 `"成功完成"`——下游正则解析不可靠
3. **延迟**：每次进度更新消耗 12-25 秒 LLM 推理时间。一个 6 步 SOP 累计额外延迟 1-2 分钟

### 用 Python 做机械字符串拼接

进度更新的本质：知道目标步骤编号、知道步骤类型、知道执行结果的状态/结论，然后用固定模式拼出一个字符串追加到正确位置。这完全是确定性的字符串操作，零理由需要 LLM。

Python 实现的结果：零延迟（微秒级别）、零幻觉（格式化输出始终遵循固定模式）、格式绝对一致（成功总是 `结果: 成功 | {conclusion} | {summary}。`，重试总是 `重试 N/M`）。

### 跳过间隙填充解决条件分支追踪

在条件 SOP 中，不是所有步骤都会执行。例如：步骤 1 检查 CPU（正常），步骤 2 是"如果 CPU 超过 80%，就调用 list_top_processes"（条件不满足，跳过），步骤 3 检查内存。如果不填充跳过标记，步骤 2 在 Plan_Steps 中保持原始文本，下一轮 Scheduler 读取时不知道步骤 2 是被跳过了还是尚未执行——可能重复执行或错误判断进度。

跳过间隙填充确保条件不满足的步骤被**显式**标记——Scheduler 不会产生歧义。

### 重试逻辑的剥离-重建策略

不是简单地追加新标记到旧标记之后，而是先完全剥离旧标记，再追加新的结果和递增后的计数。这避免了标记堆叠：3 次重试后，步骤行不会累积 3 个 `结果:` 和 3 个 `重试 N/M`。剥离后的基础文本保持干净，每次重试只保留最新的结果和计数。

### 入口保护与静默降级

当 `last_step` 无法解析时（步骤编号匹配失败），ProgressUpdater 不做任何更新直接返回。这不是异常——而是 Scheduler 输出异常时的安全降级。不更新进度优于乱更新进度。state 不变，下一轮 Scheduler 可以重新生成正确的 `NEXT_STEP`。

## 不这么做会怎样

### 保留 v1 的 LLM 进度更新

每次进度更新 12-25 秒延迟。6 步 SOP → 额外 72-150 秒，严重降低了 Agent 的交互响应。步骤文本被 LLM 改写后，Scheduler 在下一轮"读不懂"自己上一步执行的步骤的原始意图——因为原始语义已被改写。基于错误理解的下一步决策 → 工具调用错误 → 任务失败。

### 不在更新前填充跳过间隙

Scheduler 读到 `2. 如果 CPU 超过 80%，就调用 list_top_processes()`——没有状态标记。Scheduler 无法判断：这步是被跳过了，还是尚未执行？两种解读导致两种行为：跳过 vs 重新执行。Scheduler 可能错误地选择重新执行（浪费一轮 LLM + 工具调用），或者错误地跳过（忽略了 CPU 实际已超 80%）。

### 重试时不清除旧标记（标记堆叠）

3 次重试后的步骤行堆积 120 个字符的标记，使得 `_parse_steps()` 的正则分割不稳定，Scheduler Thinker 读起来也困惑。

### 没有入口保护

`last_step` 格式异常时抛出异常 → 无异常处理 → 异常传播到 LangGraph → 图执行中断 → Agent 崩溃。入口保护用零中断的方式处理这个边界情况。

### 没有重试上限

如果工具因网络超时持续失败（非工具 bug，而是外部条件），重试无限进行。`已达到重试上限` 标记是一个硬性终止——在此之后 Scheduler 必须走异常处理路径（INTERRUPT/ERROR），而不是继续重试。
