# 日志系统 — 按轮次 + 按节点的完整审计追踪

## 做了什么

CutinAgent 的日志系统围绕两个核心函数构建：`log_node_io()` 记录每个节点的 Thinker 输入/推理链/Formatter 重试/耗时/Token 用量；`log_state_snapshot()` 记录每个节点执行后的全量 state JSON 快照。文件系统按 `{session}/round_{N}/{NodeName}.txt` 组织写入 `history/` 目录。

### 日志目录结构

```
history/
└── {YYYYMMDD}_{HHMMSS}_repl_session/    # 由 repl/session_manager.py 创建
    ├── RUN_SUMMARY.txt                   # 会话级摘要
    └── round_0/                          # 第 0 轮（UserCoordinator 等 REPL 外层节点）
    │   ├── UserCoordinator.txt
    │   ├── state_UserCoordinator.json
    │   └── ...
    └── round_1/                          # 第 1 轮（SOP 执行图内循环）
        ├── SopExecutionScheduler.txt
        ├── state_SopExecutionScheduler.json
        ├── tool_get_git_diff.json        # 工具输出独立存储
        ├── ProgressUpdater.txt           # ProgressUpdater 的 before/after 对比
        └── ...
```

### 核心函数 1：log_node_io()

`utils/debug_logger.py` 的 `log_node_io()` 接收节点名、轮次号、Thinker 输入、推理链、Formatter 日志列表（每次尝试的 retry/output/valid/reason）、最终结果、会话目录、耗时、token 用量等参数，写入按 round 分目录的文本日志文件。

写入的文本文件结构清晰分段：Thinker Input 段显示节点收到的完整输入上下文，Reasoning Chain 段显示 Thinker 输出的完整推理文本，Formatter Output 段逐次显示每次重试的输出和校验结果（失败显示 `[Validation Failed] Reason: ...`，成功显示 `[Validation Passed]`），Timing & Tokens 段记录总耗时和按 thinker + 每次 formatter_try 细分的 token 统计，Final Result 段显示最终映射到 state 的字段值。

**追加模式**：如果同一 round 内同一节点被多次调用（如重试场景），后续调用以 `[追加调用]` 标记追加到原文件末尾，保证不丢失第一次调用的日志。

**Token 用量**：区分 thinker 和每次 formatter 尝试的 token 统计（Ollama 返回的原始字段被 `stream_llm()` 归一化为 `input`/`output`/`total`）。每次 Formatter 尝试都单独记录——这对于分析"为什么三次重试都失败了"至关重要：可以对比每次尝试的输入/输出 token 数变化，看是否是上下文膨胀导致的。

### 核心函数 2：log_state_snapshot()

`utils/debug_logger.py` 的 `log_state_snapshot()` 将 state dict 的完整 JSON 转储写入 `round_{N}/state_{node_name}.json`。使用 `json.dump()` 带 `ensure_ascii=False, indent=2, default=str`——`default=str` 处理所有非 JSON 可序列化类型（datetime、对象引用等）。54 个字段的当前状态被完整快照。

### 工具执行日志

每次工具调用后，ToolExecutor 单独写一个 JSON 文件（`tool_{tool_id}.json`），包含三字段完整值（status, summary, detail）加可选的执行耗时（elapsed_ms）。每个工具独立一个文件，精确对应一个工具调用。

### ProgressUpdater 日志

ProgressUpdater 自带内部日志函数，写入 `round_{N}/ProgressUpdater.txt`，记录 target_step（被更新的步骤编号）、step_type（SEQUENTIAL/CONDITIONAL/PARALLEL 等）、is_retry（布尔值）、gaps_filled（是否触发了跳过间隙填充）、elapsed（执行耗时，通常 < 1ms），以及更新前后的完整 Plan_Steps 对比文本。

### Session 管理与会话级摘要

`repl/session_manager.py` 的 `create_session_dir()` 创建时间戳目录 `{YYYYMMDD}_{HHMMSS}_repl_session`。`write_run_summary()` 在会话结束（`/exit`）时写入 `RUN_SUMMARY.txt`，包含各步骤的时序和状态摘要。

### 全局 _session_dir 与入口设置

`utils/debug_logger.py` 维护模块级 `_session_dir` 变量，通过 `set_session_dir()` 设置、`get_session_dir()` 读取。`main.py` 在启动时调用 `set_session_dir(session_dir)` 设置全局路径。节点代码通过 `state.get("session_dir", "")` 优先使用 state 中的路径，回退到全局变量——双层回退确保日志不会写入错误目录。

## 为什么这么做

### 完整审计追踪是不可协商的需求

Agent 出问题时，你需要回答六个问题：模型收到了什么输入、模型是怎么推理的、模型输出了什么且是否通过校验、整个 state 在执行前后是什么状态、每个工具实际返回了什么、每个步骤的进度标记是怎么追加的。

没有日志，Agent 是一个黑盒——你只能看到最终输出，但不知道中间哪一步出了错。对于使用 4B 模型（幻觉概率高于大模型）的系统，完整的输入/输出追踪是调试的基础工具。

### 文件系统组织（按 round + 按 node）

单一的 `app.log` 文件把所有信息串在一起，排查时需要 `grep` 和 `less` 翻几十页。按 `round_{N}/{NodeName}.txt` 组织直接对应了 Agent 的执行流程结构——"第 2 轮 Scheduler 选择了什么工具" → 直接打开 `round_2/SopExecutionScheduler.txt` 看 Reasoning Chain。

### JSON 快照 + 文本日志互补

`state_{node_name}.json` 提供可程序化分析的数据（diff 两个 JSON 看 state 变化；grep token 用量做性能分析）。`{NodeName}.txt` 提供人类可读的叙事流（看 Thinker 是怎么一步步推理的）。两者不互相替代。

### 追加模式处理节点重复调用

同一 round 内同一节点可能被多次调用的场景：Scheduler 的 Formatter 重试时再次调用了 Formatter，或 ProgressUpdater 被调用后又因 Scheduler 的 ONGOING 再次回到同一节点。追加模式确保不丢失第一次调用的日志。

### 工具执行日志独立存储

`tool_{id}.json` 独立于节点日志。原因：一个节点（ToolExecutor）可能在一次调用中执行 3 个并行工具——它们的输出不应该混在一起。每个工具独立一个 JSON 文件，精确对应一个工具调用。

## 不这么做会怎样

### 无日志系统

Agent 黑盒运行。用户报告"第三次执行时匹配了错误的 SOP"——但你无法复现。没有 Thinker 输入记录 → 不知道用户当时说了什么。没有 Reasoning Chain → 不知道模型当时是怎么推理的。没有 state snapshot → 不知道当时的 CONVERSATION_HISTORY 是什么状态。一个问题彻底无法调试。

### 只有 print 输出

终端流式输出刷屏后丢失。用户执行了 3 轮 SOP 操作，第 1 轮的 print 已经滚出终端缓冲区。事后想查"第一轮选了哪个 SOP"——需要重新运行（可能无法精确复现输入和状态）。

### 所有日志混在单一文件

排查一个问题需要在这一个文件中搜索和跳转，缺乏索引。对于一次 SOP 执行（通常涉及 3 个节点 × 多轮循环 = 10+ 个日志块），在单文件中定位特定的推理链极其低效。按 round + 按 node 的组织直接匹配了执行流程结构。

### 没有 token 使用量记录

无法回答"这个 SOP 消耗了多少 token？"——对于成本敏感的场景（即使是本地），这是重要的系统性能指标。Token 使用量记录让你可以对比不同 SOP 的上下文效率、评估 Compactor 的压缩效果、决定是否需要进一步优化 prompt。

### 没有 state JSON 快照

只有文本日志时，你只能看"模型输出了什么"。但无法回答"为什么 ToolExecutor 选择了这个工具？"——因为执行时 ToolExecutor 读的是 state 中的 `current_tool_call` 字段，而这个字段在 `state_SopExecutionScheduler.json` 中准确记录了当时的值。文本日志显示的是格式化结果，JSON 快照显示的是精确的程序状态。
