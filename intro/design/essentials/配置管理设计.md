# 配置管理系统 — 运行时配置与持久化

## 做了什么

CutinAgent 的配置管理系统支持在 REPL 运行时通过 `/config` 命令可视化调整多项运行时参数，修改后的值自动持久化到 `user/config/user_config.json`，重启后自动恢复。

### 两层配置架构

| 配置层 | 文件位置 | 用途 | 修改方式 |
|--------|---------|------|---------|
| **模型配置** | `user/config/model_config.json` | LLM 参数（model_id, temperature, top_p, num_predict 等） | 手动编辑 JSON |
| **运行时配置** | `user/config/user_config.json` | REPL 行为参数（压缩阈值、缓冲间隔、TTS 等） | `/config` 命令可视化调整 |

模型配置在 LLM 初始化时读取一次，之后不变。运行时配置在 REPL 运行期间通过 `/config` 即时调整，部分参数（如缓冲间隔）立即生效，少数参数（如输入栏行数）重启后生效。

### 模块架构

#### `repl/config_manager.py` — 数据层

维护模块级 `RUNTIME_CONFIG` 字典，提供 5 个核心函数：

| 函数 | 职责 |
|------|------|
| `load_user_config()` | 从 `user_config.json` 加载持久化值到 `RUNTIME_CONFIG`，文件不存在/损坏时保持默认值 |
| `save_user_config()` | 将 `RUNTIME_CONFIG` 写入 `user_config.json`（自动创建目录、静默忽略写入错误） |
| `get_config()` | 返回 `RUNTIME_CONFIG` 引用（调用方直接读取值） |
| `apply_config(updates)` | 批量更新（仅更新已有键、跳过同名同值），变化时自动持久化 |
| `reset_defaults()` | 恢复所有值为代码默认值，并持久化 |

**关键设计**：`load_user_config()` 在模块导入时自动调用（文件底部 `load_user_config()`），确保 REPL 启动时已恢复上次保存的配置。路径通过 `__file__` 推导项目根目录，保证从任意 CWD 启动都能找到正确的 `user/config/user_config.json`。

**类型安全**：`load_user_config()` 加载 JSON 后对数值类型做强制转换（`type(_DEFAULTS[k])(data[k])`），防止 JSON 将 `int` 解析为 `float`（如 `4096` → `4096.0`）。

#### `repl/config_picker.py` — UI 层

基于 prompt_toolkit `ConditionalContainer` 的配置选择器（11 行高度），提供可视化设置调整界面：

```
  ─────────────────────
    输入区域 (TextArea)
  ─────────────────────
  全局设置

  > 自动压缩阈值     4096 tokens  ← →
    流式缓冲间隔        2 s        ← →
    输入栏最大行数     10 行       ← →
    TTS 语音播报     开启        ← →
    TTS 语音        Xiaoxiao (女) ← →
    TTS 语速          +0%        ← →

     [ 保存 ]      [ 恢复默认 ]

  ↑ ↓ 选择  ← → 调整  Enter 保存  Esc 取消
```

### Copy-on-Activate 模式

配置选择器最关键的设计：激活时拷贝 `RUNTIME_CONFIG` → `temp_values`，用户调整修改 `temp_values`，不影响运行中的实际配置。

```
activate_config_picker:
  temp_values = dict(RUNTIME_CONFIG)   ← 拷贝

左/右调整:
  temp_values["stream_buffer_interval"] = 3   ← 只改 temp

Enter → 保存按钮:
  apply_config(temp_values)            ← 写回 RUNTIME_CONFIG + 持久化

Esc → 取消:
  temp_values 丢弃，RUNTIME_CONFIG 不变
```

如果直接修改 `RUNTIME_CONFIG`：用户调整缓冲间隔从 2→3→5→8，中途按 Esc 想取消，但 `RUNTIME_CONFIG` 已经被修改了——取消失去了意义。Copy-on-Activate 确保了取消操作的语义正确性。

### 可配置项一览

| 设置项 | 内部键 | 默认值 | 范围 | 步长 | 生效时机 | 消费方 |
|--------|--------|--------|------|------|---------|--------|
| 自动压缩阈值 | `auto_compact_threshold` | 4096 | 1024–8192 | 1024 | 即时 | `compaction_controller.py` |
| 流式缓冲间隔 | `stream_buffer_interval` | 2 | 1–60 | 1 | 即时 | 所有 LLM 调用点 |
| 输入栏最大行数 | `input_max_lines` | 10 | 1–20 | 1 | **重启** | `app_builder.py` |
| TTS 语音播报 | `tts_enabled` | `True` | 布尔 | — | 即时 | `tts_engine.py` |
| TTS 语音 | `tts_voice` | `zh-CN-XiaoxiaoNeural` | 8 种 | — | 即时 | `tts_engine.py` |
| TTS 语速 | `tts_rate` | `+0%` | -50%–100% | 10% | 即时 | `tts_engine.py` |

**半静态参数说明**：`input_max_lines` 在 `TextArea` 创建时（`app_builder.py` 的 `Dimension(max=...)`）读取一次，运行时 `/config` 修改后不会动态调整已有输入框的高度，重启 REPL 后生效。其余所有参数在每次节点/工具调用时重新读取 `get_config()`，修改即时生效。

### 配置选择器键位绑定

| 按键 | 设置行 (index 0-5) | 保存按钮 (index 6) | 恢复默认按钮 (index 7) |
|------|-------------------|--------------------|-----------------------|
| ↑ | 上移选中项 | 上移选中项 | 上移选中项 |
| ↓ | 下移选中项 | 下移选中项 | 下移选中项 |
| ← | 减少值 | — | — |
| → | 增加值 | — | — |
| Enter | 忽略（no-op） | 保存并关闭 | 恢复默认并关闭 |
| Esc | 取消（关闭且不保存） | 取消 | 取消 |

### 与另外两种选择器的互斥

Session / SOP / Config 三种选择器通过 `any_picker` 复合过滤器确保互斥——同一时刻只有一个选择器可见。详见 [ui设计文档.md](../ui设计文档.md) 第 4.1–4.2 节。

## 为什么这么做

### 持久化到 JSON 而非"仅内存"

如果不持久化，用户每次启动 REPL 后都需要重新 `/config` 调整参数（如"我喜欢缓冲间隔设为 3s"）——纯手动重复操作。持久化到 `user_config.json` 让用户的设置偏好"记住"，重启自动恢复，减少摩擦。

### Copy-on-Activate 保护运行时一致性

如果选择器的调整直接作用于 `RUNTIME_CONFIG`，会出现两个问题：
1. **取消语义失效**：用户改了几项后按 Esc，但 `RUNTIME_CONFIG` 已变——取消失去了意义
2. **中间状态污染**：用户调整缓冲间隔从 2→1 的瞬间，正在执行的 LLM 调用读到了 `1`（过于频繁 flush），然后又读到 `3`——同一轮调用中出现不一致的参数

Copy-on-Activate 隔离了"调整中"和"生效中"两个状态：调整期间运行中的 LLM 调用读到的始终是稳定值，只有用户确认保存后才切换。

### 模块导入时自动加载

`load_user_config()` 在 `config_manager.py` 被 import 时自动执行（模块级代码），而非由某个初始化函数显式调用。这确保了无论从哪个入口启动（`python main.py` / `cutin` 命令 / 测试脚本），持久化配置都能自动恢复，不依赖调用方是否记得调用 `load_user_config()`。

### 类型强制转换

JSON 标准不区分 `int` 和 `float`——`json.load("4096")` 在某些实现中返回 `4096.0`。如果 `auto_compact_threshold` 的值从 `4096` 变成 `4096.0`，类型比较 `RUNTIME_CONFIG[k] != updates[k]` 将始终为 `True`（因为 `4096 != 4096.0`），导致每次 `/config` 保存时都执行不必要的持久化写入。`type(_DEFAULTS[k])(data[k])` 强制类型转换消除了这个问题。

### 静默降级（写入失败不崩溃）

`save_user_config()` 在磁盘满、权限不足等场景下写入失败时，仅跳过持久化（值仍在内存中生效，当前 REPL 会话正常），不抛异常中断流程。这遵循了"配置持久化是辅助功能"的原则——即使保存失败，用户当前的设置调整在当前会话中仍然有效。

### 配置选择器复用 Condition 互斥机制

配置选择器没有新建独立的 Application 或 PromptSession，而是复用现有 prompt_toolkit Application 和 `ConditionalContainer` 机制。这与 Session / SOP 选择器完全一致：三种选择器共享同一个事件循环、同一套按键绑定架构、同一个 `any_picker` 互斥过滤器。新增配置选择器时不需要增加新的事件循环、线程模型或按键绑定系统。

## 不这么做会怎样

### 不持久化配置

用户每次启动 REPL 都需要手动调整参数。如果默认缓冲间隔是 2s 但用户偏好 1s（希望更快看到流式输出），每次启动都要记得改——"忘记改 → 这次体验不好 → 想起来已经晚了"的循环反复出现。

### 不隔离 temp_values

用户打开配置选择器，把缓冲间隔从 2 调到 1，正准备调别的，收到一条中文消息（正在执行的 LLM 刚好 flush 了输出）。因为缓冲间隔已经改为 1，flush 频率翻倍——但用户还没决定要不要保存这个值。中间状态影响了当前运行的 LLM 调用。

### 配置选择器不做互斥

三种选择器（Session / SOP / Config）可能同时激活并争夺底部区域。用户同时看到会话列表和配置面板——按键操作（↑ ↓ Enter Esc）应该影响哪个选择器？没有 `any_picker` 互斥机制，三种选择器的按键绑定会互相干扰。

### 不处理类型强制转换

JSON 加载后 `4096` 变成 `4096.0`（float）。`apply_config()` 比较 `4096 != 4096.0` → 判定为变化 → 每次保存都执行 `save_user_config()`。用户退出 REPL 时发现 `user_config.json` 的修改时间是"刚刚"——明明什么都没改，文件却被重新写入了一遍。
