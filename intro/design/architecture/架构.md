# CutinAgent 架构论述

## 双层架构总览

CutinAgent 采用 **REPL 外层 + LangGraph 内层** 的双层架构。这不是简单的模块划分——两层分别解决不同性质的问题，且**代码判断与 LLM 判断的边界恰好落在这条分界线上**。

```
REPL 外层（人机协作）              LangGraph 内层（SOP 执行）
┌─────────────────────────┐      ┌─────────────────────────┐
│  UserCoordinator        │      │  SopExecutionScheduler  │
│  → 意图分类 + 渐进确认    │      │  → 读进度 → 定位步骤      │
│  → IS_EXECUTE 闸门       │      │  → 生成工具调用           │
│       ↓                 │      │       ↓                 │
│  [用户 y/n 确认]         │      │  ToolExecutor           │
│       ↓                 │      │  → 分发执行 → 存储变量    │
│  加载 SOP               │      │       ↓                 │
│       ↓                 │      │  ProgressUpdater        │
│  ═══════════════════    │      │  → 机械追加进度标记       │
│       ↓                 │      │       ↓                 │
│  Compactor              │      │  (循环回 Scheduler)      │
│  → 评价 + 历史压缩       │      │                         │
└─────────────────────────┘      └─────────────────────────┘
   对话与控制                         机械式步骤推进
   人做最终决策                       代码做路由判断
```

**外层管"做不做、做什么"**——这是需要人类判断的领域。UserCoordinator 用 LLM 理解用户意图，但**最终执行权在 IS_EXECUTE 闸门**，闸门是代码开关，用户必须显式输入 `y`。

**内层管"怎么做"**——SOP 文件已经写好了步骤，不需要 LLM 再"思考该做什么"。内层的 LLM（Scheduler）只做一件事：读进度标记 → 定位下一步 → 生成工具调用。其余的——工具执行、进度更新、循环路由——全是代码。

---

## 五个核心组件

### 1. UserCoordinator — 人机协作网关

**解决什么**：自主 Agent 从用户意图直接跳到执行，没有中间确认环节。Agent 可能因为理解偏差执行错误操作，用户没有机会审查和纠正。

**输入**：
- `user_instruction`：用户当前输入
- `current_dialogue`：本轮完整对话记录
- `conversation_history`：历史对话压缩摘要
- `execution_history`：历史执行压缩摘要
- `SOP_LIBRARY`：可用 SOP 索引文本（由 `build_sop_library_from_ids()` 从 `sop_ids` 构建，格式为 `SOP_ID | Objective | Description`）

**输出（五字段）**：
- `chat_message`：始终非空的对话回复
- `sop_id`：匹配到的 SOP 标识符
- `current_action`：具体行动描述
- `long_term_intent`：长远意图
- `is_execute`：`"true"` 或 `"false"`

**三级渐进式确认**：

```
Stage 1 (SOP匹配)         Stage 2 (行动细化)         Stage 3 (最终确认)
┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐
│ 推荐 SOP          │      │ 确认缺失信息      │      │ 展示完整摘要      │
│ "是这个任务吗？"    │ ──→  │ 提供默认值        │ ──→  │ LONG_TERM_INTENT │
│ IS_EXECUTE=false  │      │ IS_EXECUTE=false  │      │ IS_EXECUTE=true   │
│ SOP_ID 填充        │      │ + ACTION 填充     │      │ 五字段全部填充     │
└─────────────────┘      └─────────────────┘      └──────┬──────────┘
                                                         │
                                                   用户输入 y/n
```

**为什么不是 LLM 判断**：

IS_EXECUTE 闸门是**代码硬开关**，不是 LLM 说了算。LLM 输出 `is_execute="true"` 只是"建议执行"，真正的执行权在 `main.py`：代码检查 `is_execute == "true"` 后弹出 `y/n` 确认提示，只有用户显式输入 `y` 才加载 SOP 并进入 LangGraph 执行图，否则重新进入对话循环。

Validator（`UserCoordinatorValidator.py`）在 LLM 输出之后、代码路由之前做白名单校验：SOP_ID 必须在 `sops.csv` 中真实存在，`is_execute="true"` 时 `LONG_TERM_INTENT` 必须非空。校验失败 → Formatter 重试（最多 3 次）→ 仍失败则流程中断。

**设计原则**：LLM 负责"理解"——用户想做什么、匹配哪个 SOP、需要补充什么信息。代码负责"把关"——SOP 是否存在、格式是否正确、用户是否确认。两者边界清晰，互不侵入。

---

### 2. Compactor — 执行评价与历史压缩

**解决什么**：多轮 Agent 对话中，原始对话和执行日志持续膨胀，4B 模型的 8K 上下文窗口很快被填满。需要在不丢失关键信息的前提下压缩历史。

**输入**：
- `current_dialogue`：本轮完整对话
- `conversation_history`：累积的历史对话摘要
- `execution_history`：累积的历史执行摘要
- `current_action`：本次执行的目标
- SOP 执行结果（`execution_result`, `task_status` 等）

**输出（三字段）**：
- `evaluation`：1-2 句，SOP 是否达成目标
- `conversation_summary`：2-4 句对话摘要
- `execution_summary`：2-4 句执行摘要

**为什么不是 LLM 判断**：

Compactor 的 LLM 只负责**生成摘要文本**——这是 LLM 擅长的事。但摘要的**生命周期管理**完全由代码控制：

- **何时压缩**：代码决定——SOP 执行完毕后必定运行 Compactor
- **是否保留**：代码决定——用户满意（输入 `y`）才将 `compactor_conversation_summary` 和 `compactor_execution_summary` 追加到长期历史；不满意则丢弃
- **何时清除对话**：代码决定——仅在用户满意后才清空 `current_dialogue`，不满意则保留供继续调整

LLM 做它擅长的（文本摘要），代码做它擅长的（状态生命周期管理）。

---

### 3. SopExecutionScheduler — 步骤调度与工具调用

**解决什么**：SOP 的 Plan_Steps 是一段自然语言文本，需要有人"读懂"当前执行到哪一步、下一步该做什么、用什么工具、传什么参数。这是 4B 模型在内层的唯一 LLM 节点。

**输入**：
- `sop_plan_steps`：带进度标记的 Plan_Steps（如 "1. 调用 xxx 结果: 成功 | CPU 2.9%。"）
- `sop_exception_handling`：全局异常处理规则
- `execution_result`：上一步工具执行结果
- `current_round`：当前轮次

**输出**：
- `current_tool_call` / `current_tool_calls`：单个或并行的工具调用
- `task_status`：`ONGOING` / `FINISH` / `ERROR` / `INTERRUPT`
- `last_step`：当前执行的步骤编号（如 "2"）

**为什么路由是代码判断**：

Scheduler 输出的 `task_status` 看起来是 LLM 决定的，但**路由本身是代码硬编码的**：`graph/Builder.py` 的 `route_after_scheduler()` 读取 `state.get("task_status", "ONGOING")`，值为 `"ONGOING"` 时返回 `"tool_executor"` 进入执行循环，其他值（FINISH / ERROR / INTERRUPT）全部返回 END 终止图。

这不是让 LLM 决定"下一步去哪个节点"——LLM 只输出一个字符串，代码根据这个字符串做路由。四种状态的含义和路由规则是写死在代码里的：

| task_status | 代码行为 | 含义 |
|------------|---------|------|
| `ONGOING` | → ToolExecutor → ProgressUpdater → 循环回 Scheduler | 还有步骤未完成 |
| `FINISH` | → END | 所有步骤已完成，正常退出 |
| `ERROR` | → END | 关键工具失败，异常退出 |
| `INTERRUPT` | → END | 需要人工判断，暂停退出 |

**设计原则**：LLM 负责"读进度、选工具"（需要语义理解），代码负责"往哪走"（需要确定性）。图的结构（节点 + 边）是编译时确定的，运行时不变。

---

### 4. ToolExecutor — 工具分发与变量存储

**解决什么**：Scheduler 输出了工具名和参数，需要有东西去真正执行它，并把结果格式化后传递给下游。**这个节点完全不需要 LLM**。

**输入**：
- `current_tool_call` / `current_tool_calls`：Scheduler 输出的工具调用（支持单个或并行多个）
- `current_round`：当前轮次
- `session_dir`：会话日志目录

**输出**：
- `execution_result`：拼接后的结果字符串（如 "成功 | CPU 2.9%（正常） | 系统资源正常"）
- `tool_status`：`"成功"` 或 `"失败"`
- `tool_conclusion`：结论/原因
- `tool_summary`：精简摘要
- `tool_detail_var`：变量名（如 `VAR_get_system_health`）

**纯代码流程**：

```
Scheduler 输出 TOOL_CALL
        │
        ▼
ToolDispatcher.dispatch(tool_id, tool_args)
        │
        ▼
工具返回 {"status", "conclusion", "summary", "detail"}
        │
        ├── detail 非空 → VariableStore.store(detail, tool_id)
        │                 生成变量名 VAR_{tool_id}
        │
        └── 拼接 execution_result = "成功 | conclusion | summary"
```

**工具四字段契约**：所有 11 个工具必须返回统一格式。这是代码层面的约定，不是 LLM prompt 的约定——ToolExecutor 用 `fields.get("status", "")` 解析，字段缺失不会导致崩溃。

**为什么不需要 LLM**：工具执行是机械操作——接收函数名和参数，调用函数，返回结果。不需要语义理解。ToolDispatcher 用 Python 字典做路由（`toolbox[tool_id](**args)`），比 LLM 快 3 个数量级且不会出错。

---

### 5. ProgressUpdater — 纯代码进度更新

**解决什么**：SOP 执行需要"划掉已完成步骤"的机制——让 Scheduler 在下一轮能看清哪些步骤做完了、哪些跳过了、哪些需要重试。这是整个内循环中**最不应该用 LLM 的环节**。

**为什么不用 LLM**：

v1 尝试过用 LLM（ProgressSummarizer）做进度更新，结果是：
- LLM 可能"创造性"地改写步骤文本，改变原有语义
- 格式不一致（同样的"完成"有时写"已完成"，有时写"执行完毕"）
- 额外消耗 12-25 秒推理时间
- 可能遗漏步骤或错误标记

进度更新本质是**机械的字符串拼接**——知道目标步骤编号、知道步骤类型、知道执行结果，就能用确定性的规则拼出进度标记。

**输入**：
- `sop_plan_steps`：当前 Plan_Steps 文本
- `last_step`：Scheduler 输出的步骤编号
- `tool_status` / `tool_conclusion` / `tool_summary` / `tool_detail_var`：执行结果四字段
- `retry_limit`：重试上限

**输出**：
- `sop_plan_steps`：更新后的 Plan_Steps（追加了进度标记）
- `current_round`：递增 1

**四种机械更新模式**：

```
步骤类型        更新前                           更新后
──────────────────────────────────────────────────────────────────
顺序/并行      1. 调用 get_system_health()      1. 调用 get_system_health()
                                                 结果: 成功 | CPU 2.9% | 系统正常。

条件           2. 如果 CPU>80%，就调用          2. 因为 CPU=2.9% 未触发条件，
                 list_top_processes()              步骤已跳过。

重试           3. 调用 check_port()             3. 调用 check_port()
                结果: 失败 | 连接超时。            结果: 失败 | 连接超时。
                重试 1/3                           重试 2/3

跳过间隙       步骤1已完成，步骤3正在执行        步骤2 自动标记为 已跳过（条件不满足）。
（自动填补）
```

**代码流程**：`progress_updater_node()` 按五步机械执行——（1）用 `_parse_steps()` 将 Plan_Steps 文本解析为步骤列表；（2）按编号精确匹配定位目标步骤；（3）调用 `_fill_skipped_gaps()` 填补跳过间隙（如步骤 1 完成后直接到步骤 3，则步骤 2 自动标记"已跳过"）；（4）根据步骤类型和是否为重试，走对应的更新分支——重试走 `_update_with_retry()` 递增计数，顺序步骤走 `_update_sequential()` 追加结果，条件步骤走 `_update_conditional()` 追加因果说明；（5）调用 `_reconstruct_plan()` 将步骤列表重建为文本。

整个过程纯字符串操作，不调 LLM，不涉及语义理解。步骤类型的分类（`_classify_step`）是正则匹配，不是 LLM 判断。

## 架构原则总结

### 代码判断 vs LLM 判断的分界线

```
┌─────────────────────────────────────────────────────────┐
│  需要语义理解的事 → LLM 做                                │
│  · 用户想做什么（意图分类）                                │
│  · 匹配哪个 SOP（语义相似度）                              │
│  · 当前执行到哪一步（读进度标记）                           │
│  · 选什么工具、传什么参数（步骤语义 → 函数调用）             │
│  · 对话/执行摘要怎么压缩（文本总结）                        │
├─────────────────────────────────────────────────────────┤
│  需要确定性的事 → 代码做                                   │
│  · SOP_ID 是否真实存在（白名单校验）                        │
│  · IS_EXECUTE 闸门（用户必须输入 y）                       │
│  · 工具分发与执行（字典路由）                               │
│  · 进度标记追加（字符串拼接）                               │
│  · 循环/退出路由（task_status 字符串比对）                  │
│  · 历史生命周管理（何时累积、何时清除）                      │
└─────────────────────────────────────────────────────────┘
```

### 数据流：从用户输入到执行完毕

```
User: "帮我全面检查系统状态"
  │
  ▼
[UserCoordinator] LLM: 匹配 FULL_SYSTEM_HEALTH_CHECK
  │ 输出: SOP_ID= FULL_SYSTEM_HEALTH_CHECK, IS_EXECUTE=true
  ▼
[Validator] 代码: SOP_ID 白名单 ✓, 五字段格式 ✓
  ▼
[IS_EXECUTE Gate] 代码: 展示摘要 → 等待用户 y/n
  │ 用户输入 y
  ▼
[load_sop_markdown] 代码: 解析 Markdown → SopSpecChecker 校验
  │
  ▼  ═══════════ 进入 LangGraph 内层 ═══════════
  │
  ▼
[Scheduler] LLM: 读 Plan_Steps → 定位步骤1 → TOOL_CALL: get_system_health()
  │ 输出: task_status=ONGOING
  ▼
[route_after_scheduler] 代码: ONGOING → tool_executor
  ▼
[ToolExecutor] 代码: dispatch("get_system_health") → "成功 | CPU 2.9%"
  │ detail 非空 → VariableStore["VAR_get_system_health"] = raw_data
  ▼
[ProgressUpdater] 代码: 步骤1 顺序模式 → 追加 "结果: 成功 | CPU 2.9%"
  ▼
(无条件循环回 Scheduler)
  ▼
[Scheduler] LLM: 看到步骤1已标记 → 检查步骤2条件 → CPU<80% → 跳过步骤2
  │ → 所有步骤已标记 → task_status=FINISH
  ▼
[route_after_scheduler] 代码: FINISH → END
  │
  ▼  ═══════════ 退出 LangGraph 内层 ═══════════
  │
  ▼
[Compactor] LLM: 评价 + 对话摘要 + 执行摘要
  ▼
[代码] 用户满意 y → 累积历史 + 清除对话
```

### 三个核心架构决策

**1. SOP 是决策中心，LLM 是执行器**

不是 "LLM 自主决定做什么"，而是 "SOP 文件定义步骤，LLM 按步骤执行"。决策权在人类编写的 Markdown 文件中，LLM 的职责被收窄为：理解步骤语义 → 提取参数 → 调用工具。出问题时检查 SOP 文件而非逆向分析黑盒模型。

**2. 每个 LLM 节点后都有代码校验**

```
Thinker (0.4) → Formatter (0.0) → Validator (代码) → 路由 (代码)
    ↑                ↑                ↑              ↑
  自由推理         确定性提取       白名单校验      确定性路由
```

不是 "相信 LLM 输出"，而是 "LLM 建议 → 代码验证 → 代码执行"。Formatter 零温度 + Validator 白名单 + 代码路由，三层防线确保 4B 模型的输出不导致系统崩溃。

**3. 内层最小化 LLM 参与**

LangGraph 内层的三个节点中，只有一个（Scheduler）调用 LLM。另外两个（ToolExecutor、ProgressUpdater）是纯代码。循环路由也是纯代码。整个执行循环中，LLM 只在"需要读进度、选工具"的时候被调用——其他操作都是确定性的，不应该消耗 12-25 秒的推理时间。
