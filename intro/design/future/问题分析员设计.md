# 问题分析员 (Problem Analyzer) — 自主信息收集层

> **状态：设计提案 (RFC)** — 尚未实现。本文档描述 v0.2 计划引入的架构变更。
>
> **关联设计**：[[UserCoordinator设计]](../essentials/UserCoordinator设计.md) · [[工具合约设计]](../essentials/工具合约设计.md) · [[Compactor设计]](../essentials/Compactor设计.md) · [[子SOP嵌套设计](子SOP嵌套设计.md)

## 做了什么

在 UserCoordinator 之前插入一个**问题分析员 (Problem Analyzer)** 节点，它无需用户确认即可自主调用所有只读类信息收集工具，对用户任务进行全面的前置分析，最终向 UserCoordinator 输出问题理解报告和候选解决方案。

### 当前架构的缺口

CutinAgent 目前的三层架构是：

```
UserCoordinator（意图理解 + 确认） → SopExecutionScheduler（步骤调度） → ToolExecutor（工具执行）
```

这个架构在一个关键场景中存在盲区：**用户描述模糊，LLM 需要主动收集信息才能理解问题**。例如：

- 用户说 "我的系统有点卡" → 需要收集 CPU/内存/磁盘/进程信息才能判断
- 用户说 "帮我整理最近的提交" → 需要先查看 git log 才知道最近做了什么
- 用户说 "检查一下服务状态" → 需要先知道有哪些服务、哪些端口

当前流程中，UserCoordinator 必须在**第一轮**就完成意图理解 → SOP 匹配 → 输出 CHAT_MESSAGE。它手里只有用户的原始输入和压缩过的历史摘要——没有实时系统信息。它只能"猜测"用户的问题，然后在聊天回复中建议用户使用某个 SOP，或者直接匹配一个不完全合适的 SOP。

问题分析员填补这个缺口：**在匹配 SOP 之前，先用工具收集信息，让 LLM 带着"看清问题全貌"的上下文进入 UserCoordinator。**

### 新四层架构

```
ProblemAnalyzer（信息收集 + 问题分析） → UserCoordinator（意图理解 + 确认） → SopExecutionScheduler（步骤调度） → ToolExecutor（工具执行）
```

### 节点定位

| 维度 | Problem Analyzer | UserCoordinator |
|------|-----------------|-----------------|
| **位置** | REPL 外层，UserCoordinator 之前 | 原位置不变 |
| **触发方式** | 每轮用户输入后自动运行 | 同现有一致 |
| **工具调用权限** | 仅只读工具 | 无工具调用 |
| **用户确认** | 无需确认，自主执行 | 三级渐进确认（不变） |
| **输出** | 问题分析报告 + 候选解决方案 | 五字段（不变） |
| **LLM 温度** | Thinker 0.4 / Formatter 0.0 | 不变 |
| **最大工具调用轮数** | 由配置项 `analyzer_max_rounds` 控制（默认 5） | 不涉及 |

### 工作流程

```
用户输入
  │
  ▼
┌──────────────────────────────────────────────┐
│ Problem Analyzer (可选的自主信息收集循环)      │
│                                              │
│  1. Thinker：分析当前已知信息，决定是否需要    │
│     调用工具收集更多信息                       │
│  2. 若需要且未达上限 → 调用只读工具 → 结果追加 │
│     到分析上下文 → 回到步骤 1                  │
│  3. 若信息充分或达上限 → Formatter 输出：     │
│     PROBLEM_ANALYSIS（问题分析）               │
│     CANDIDATE_SOP_IDS（候选SOP，可为空）       │
│     GATHERED_DATA（收集到的关键数据摘要）       │
│     NEEDS_USER_CLARIFICATION（是否需要用户澄清）│
└──────────────────────────────────────────────┘
  │
  ▼
┌──────────────────────────────────────────────┐
│ UserCoordinator (增强输入)                     │
│                                              │
│  接收 Problem Analyzer 的分析报告作为额外输入， │
│  在其基础上做 SOP 匹配 + 渐进确认。             │
│  输入新增字段：                               │
│  PROBLEM_ANALYSIS + GATHERED_DATA +            │
│  CANDIDATE_SOP_IDS                            │
└──────────────────────────────────────────────┘
  │
  ▼
  (后续流程不变)
```

### 工具权限模型变更

`tools/tools.csv` 新增一列 `Permission`，取值：

| 值 | 含义 | 可被谁调用 |
|----|------|-----------|
| `readonly` | 只读，无副作用 | Problem Analyzer + Scheduler |
| `write` | 有写操作 | 仅 Scheduler（需用户确认后） |

当前所有工具分类：

| Tool_ID | Permission | 理由 |
|---------|-----------|------|
| get_git_status | readonly | 纯查询 |
| get_git_diff | readonly | 纯查询 |
| get_git_log | readonly | 纯查询 |
| generate_commit_message | readonly | 调用 LLM 生成文本，无副作用 |
| generate_daily_report | readonly | 同上 |
| git_commit | write | 写入 Git 历史 |

扩展子中的 Linux 诊断工具全部标记为 readonly（get_system_health, list_top_processes, grep_log_content, check_network_port, check_file_access, read_env_vars, locate_large_files, test_connection, check_system_sync, get_service_status）。

### Problem Analyzer 的 Thinker Prompt 引导

Thinker 按以下步骤推理（正面引导模板）：

1. **理解用户陈述**：用户的自然语言在描述什么？
2. **判断信息缺口**：要准确理解这个问题，我还缺什么信息？
3. **决策**：是否需要调用工具收集信息？
   - 如果是简单闲聊（"你好"、"今天天气怎么样"）→ 不需要分析，直接标记为 SKIP，后续 Formatter 输出空分析
   - 如果问题明确且匹配现有 SOP（"帮我提交代码"）→ 可以快速分析，1-2 个工具确认状态即可
   - 如果问题模糊（"系统有点问题"）→ 需要多轮信息收集，逐步缩小范围
4. **如果需要工具**：从只读工具集中选择最相关的工具。优先选择能覆盖更多信息维度的工具（如 get_system_health 而非逐个调用 CPU/内存/磁盘检查）
5. **收到结果后**：评估信息是否充分。如果仍然存在关键缺口，继续收集；如果信息充分，准备输出分析报告
6. **如果需要用户澄清**：明确告诉 UserCoordinator 需要向用户确认什么

### 终止条件

Problem Analyzer 的自主循环在以下条件下终止：

1. **SKIP**：Thinker 判断不需要信息收集（闲聊/命令/已明确的任务）
2. **SUFFICIENT**：Thinker 判断信息充分，可以输出分析报告
3. **MAX_ROUNDS**：工具调用轮数达到 `analyzer_max_rounds`（默认 5）
4. **NEEDS_CLARIFICATION**：Thinker 判断需要用户澄清，继续收集信息也无法推进

### State 字段新增

```python
# OverallState 新增字段（TypedDict 扩展）
analyzer_enabled: str              # "true" / "false"，由配置控制
analyzer_problem_analysis: str     # Problem Analyzer 的问题分析报告
analyzer_gathered_data: str        # 收集到的关键数据摘要
analyzer_candidate_sop_ids: str    # 候选 SOP ID 列表（逗号分隔）
analyzer_needs_clarification: str  # "true" / "false"
analyzer_rounds_used: int          # 实际使用的工具调用轮数
analyzer_skip: str                 # "true" / "false"，Thinker 判定无需分析
```

### REPL 主循环变更（main.py 简化示意）

```python
# 在 _handle_input 中，普通消息处理流程改为：

# --- Problem Analyzer (新增) ---
if get_config().get("analyzer_enabled", False) and not is_command:
    analyzer_result = await run_llm_node(
        "ProblemAnalyzer", problem_analyzer_fn, state,
        top_status_data, app, console
    )
    state.update(analyzer_result)

    # 如果分析员认为需要用户澄清，直接回复用户，不进入 UserCoordinator
    if state.get("analyzer_needs_clarification") == "true":
        print_agent_message(console, state["analyzer_problem_analysis"])
        state["current_dialogue"].append({
            "role": "agent", "content": state["analyzer_problem_analysis"]
        })
        return

# --- UserCoordinator (增强输入) ---
# Thinker 输入中增加：
# PROBLEM_ANALYSIS: {state["analyzer_problem_analysis"]}
# GATHERED_DATA: {state["analyzer_gathered_data"]}
# CANDIDATE_SOP_IDS: {state["analyzer_candidate_sop_ids"]}
```

### 配置项

`user/config/user_config.json` 新增：

```json
{
    "analyzer_enabled": true,
    "analyzer_max_rounds": 5
}
```

用户可以通过 `/config` 选择器开关分析员功能或调整最大轮数。默认开启（`true`），因为分析员完全自主、无副作用——用户不需要额外的确认负担。

## 为什么这么做

### 当前架构的人机协作只有一个方向：从人到模型

现有流程是：用户描述 → UserCoordinator 理解 → 如果不够清楚，UserCoordinator 生成确认问题 → 用户回答 → 再理解。这个循环中，**模型始终是被动接收信息的一方**，它不会主动去"看"系统状态。

对于 "系统有点卡" 这样的问题，UserCoordinator 手里只有这句话，它只能回复 "能描述一下具体哪里卡吗？CPU 高还是内存高？" —— 但这恰恰是用户在问模型的问题。用户期望的是 Agent 自己去查，而不是把问题抛回来。

问题分析员的引入改变了信息流向：**模型可以主动获取信息，而不只是被动等待用户提供。**

### 模仿 Claude Code 的"先理解后规划"模式

Claude Code 在处理模糊请求时，会先读文件、看目录结构、查 git 状态——在充分理解代码库现状之后，才提出解决方案。这个"信息收集 → 理解 → 规划 → 确认 → 执行"的流程，是它比传统 Chat 模型更实用的关键。

CutinAgent 的当前架构已经做好了"规划 → 确认 → 执行"（UserCoordinator + Scheduler + ToolExecutor），缺少的是最前面的"信息收集 → 理解"环节。问题分析员补齐这个环节。

### 为什么放在 UserCoordinator 之前而不是之内

一个直觉上的方案是在 UserCoordinator 的 Thinker 中增加"分析当前问题"的推理步骤。但这有两个问题：

1. **UserCoordinator 不调用工具**，它只能基于用户提供的文本和压缩历史做推理。没有实时数据，再强的推理也是"盲猜"。
2. **增加 UserCoordinator 的职责会让它更复杂**。当前 UserCoordinator 的五字段输出 + 三级渐进确认已经是一个完整的人机协作协议。把信息收集塞进去会让 Thinker prompt 膨胀、推理链变长、Formatter 提取更困难。

独立节点让每个角色职责单一：分析员只管"看清问题"，协调员只管"确认并交付执行"。

### 只读权限是零风险的信息收集

分析员只能调用 `Permission=readonly` 的工具。最坏情况：4B 模型幻觉导致分析员误读了某个文件内容或端口状态——结果是分析报告不准确，UserCoordinator 可能匹配了次优 SOP。但**没有写操作被执行**，用户的系统状态不变。

这种"分析错误最多导致次优匹配"的代价，远小于"跳过分析直接执行错误的 SOP"。

如果分析员拥有写权限，幻觉可能导致 `git commit` 在用户不知情的情况下被执行——这在安全上是不可接受的，也违背了 UserCoordinator 的 IS_EXECUTE 闸门设计。

### 为什么需要 NEEDS_USER_CLARIFICATION 出口

有些问题即使调用了所有相关工具也无法自动解决。例如用户说"帮我修一下那个东西"——"那个东西"是什么？Agent 收集了一圈系统信息，依然不知道用户指的究竟是什么。

这时与其继续猜（浪费 token 和时间），不如尽早向用户澄清。"我不知道你在说什么"比"我猜了一个方向然后做错了"要好得多。这个出口让分析员在收益递减时及时止损。

### 设计为可选模块而非强制路径

`analyzer_enabled` 配置开关让分析员成为可选模块。原因：

- 闲聊场景（"你好"、"今天天气怎么样"）不需要信息收集，强制运行浪费 token
- 部分用户偏好快速响应，宁可让 UserCoordinator 直接处理
- v0.2 引入新模块时，开关允许用户在遇到问题时快速回退到 v0.1 行为

### 分析报告作为 UserCoordinator 的增强输入，而非替代

分析员的输出**增强**了 UserCoordinator 的输入，而不是替代它。UserCoordinator 仍然接收 `USER_MESSAGE`、`CURRENT_DIALOGUE`、`CONVERSATION_HISTORY`、`EXECUTION_HISTORY`、`SOP_LIBRARY`，同时新增 `PROBLEM_ANALYSIS`、`GATHERED_DATA`、`CANDIDATE_SOP_IDS`。

这意味着分析报告是"建议"性质的——UserCoordinator 可以采纳分析员的候选 SOP 建议，也可以根据与用户的对话上下文独立判断。这种**协商式而非命令式**的信息传递，保留了两层各自的专业判断空间。

## 不这么做会怎样

### 继续用当前架构处理模糊问题

用户说 "系统有点卡" → UserCoordinator 没有系统数据 → 只能输出 "你的系统可能负载较高，我建议使用 FULL_SYSTEM_HEALTH_CHECK SOP 来检查。你确认吗？" 

这个回复的问题在于：
- 用户不知道自己需要确认什么（SOP 名称对用户没有意义）
- 如果系统其实不卡（只是某个应用 UI 响应慢），Agent 匹配了错误的 SOP
- 浪费了一轮对话——用户说 "是"，然后 SOP 执行，然后发现其实不是系统问题

有了分析员：自动收集 CPU/内存/磁盘/进程数据 → 分析报告 "CPU 8% 正常，内存 75% 偏高，top 5 进程中 Chrome 占用 4.2GB，建议关闭多余的 Chrome 标签页" → UserCoordinator 基于这个报告做渐进确认 → 对话质量从 "盲猜" 提升到 "有数据支撑的建议"。

### 在 UserCoordinator 内部实现信息收集

UserCoordinator 的 Thinker prompt 需要额外描述"在什么情况下应该建议调用工具"，Formatter 输出需要增加第六个字段（工具调用），Validator 需要增加对应的校验规则。最致命的是，`if state.get("is_execute") == "true"` 这个硬开关**只管 SOP 执行不管信息收集**——框架需要一个新的执行路径来分发自主任意工具调用。

结果：UserCoordinator 变成两个角色强行塞在一个节点里——一个负责信息收集（自主），一个负责意图确认（人机协作）。两个角色的 prompt 互相干扰，Formatter 输出格式脆弱性翻倍。

### 给分析员写权限

"有些工具虽然写数据，但也只是生成报告（如 generate_commit_message 调 LLM），没有破坏性的副作用，给分析员有什么关系？"

边界是模糊的。`generate_commit_message` 确实只调用 LLM，但 `git_commit` 确实会修改 Git 历史。一旦开了"有些写操作也可以"的口子，后面每个新工具都需要在"安全 / 不安全"的灰色地带做判断。`Permission=readonly` 是清晰的白/黑二分——没有灰色地带。

### 不做信息收集，直接让用户提供所有信息

这是 ChatGPT 的模式：用户需要自己描述清楚问题，模型才能给出有用的回答。但对于 Agent 来说，如果用户需要先 `top`、`df`、`ss` 各跑一遍再把结果贴给 Agent——那 Agent 的工具执行能力就成了摆设。

Agent 的价值就在于**替用户执行这些步骤**。信息收集是 Agent 执行能力的第一步，不应该外包回给用户。

### 分析员成为必选路径

如果去掉 `analyzer_enabled` 开关，每次输入都经过分析员 → 闲聊 "你好" 也走一遍分析流程 → Thinker 判断 SKIP → 浪费一次 LLM 调用（~0.5-1s 延迟 + token 消耗）。开关让用户在"快速"和"深度"之间选择，保留了 v0.1 的轻量路径。
