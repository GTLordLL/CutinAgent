## 做了什么

在 UserCoordinator 之前插入一个**问题分析员 (Problem Analyzer)** 节点，按"是什么 → 为什么"两步推理框架，自主调用只读工具收集信息、归纳事实、推断用户意图，最终向 UserCoordinator 输出增强的分析上下文。

### 核心职责划分

问题分析员与 UserCoordinator 按通用问题解决范式分工：

```
问题分析员                      用户协作员
──────────                    ──────────
是什么 (WHAT)     ──数据流──→  怎么办 (HOW)
为什么 (WHY)                   意图匹配 → SOP 选择 → 渐进确认 → 执行
```

- **问题分析员** (WHAT + WHY)：自主调用只读工具，收集事实数据，归纳系统/仓库现状，推断用户的核心意图和需求
- **用户协作员** (HOW)：基于分析员输出的事实和意图推断，做 SOP 匹配 + 三级渐进确认 + IS_EXECUTE 闸门

分析员**不做 SOP 匹配、不反问用户、不推荐解决方案**。它纯粹是一个"看清问题全貌"的自主前置层。

### 当前架构的缺口

CutinAgent 目前的三层架构是：

```
UserCoordinator（意图理解 + 确认） → SopExecutionScheduler（步骤调度） → ToolExecutor（工具执行）
```

这个架构在一个关键场景中存在盲区：**用户描述模糊，LLM 需要主动收集信息才能理解问题**。例如：

- 用户说 "我的系统有点卡" → 需要收集 CPU/内存/磁盘/进程信息才能判断
- 用户说 "帮我整理最近的提交" → 需要先查看 git log 才知道最近做了什么
- 用户说 "检查一下服务状态" → 需要先知道有哪些服务、哪些端口

当前流程中，UserCoordinator 必须在**第一轮**就完成意图理解 → SOP 匹配 → 输出 CHAT_MESSAGE。它手里只有用户的原始输入和压缩过的历史摘要——没有实时系统信息。它只能"猜测"用户的问题，然后在聊天回复中建议用户使用某个 SOP，或者直接匹配一个不完全合适的 SOP。

问题分析员填补这个缺口：**在匹配 SOP 之前，先用工具收集信息，回答"是什么"和"为什么"，让 UserCoordinator 带着事实和意图推断进入"怎么办"。**

### 新架构

```
ProblemAnalyzer（WHAT + WHY） → UserCoordinator（HOW：意图匹配 + 确认） → SopExecutionScheduler → ToolExecutor
```

### 节点定位

| 维度 | Problem Analyzer | UserCoordinator |
|------|-----------------|-----------------|
| **位置** | REPL 外层，UserCoordinator 之前 | 原位置不变 |
| **职责** | WHAT（事实归纳）+ WHY（意图推断） | HOW（SOP 匹配 + 渐进确认 + 执行） |
| **触发方式** | 每轮用户输入后自动运行 | 同现有一致（分析员之后） |
| **工具调用权限** | 仅 `Permission=readonly` 的只读工具 | 无工具调用 |
| **SOP 输入** | **不输入任何 SOP** | 输入操作任务类 SOP |
| **用户确认** | 无需确认，自主执行 | 三级渐进确认（不变） |
| **反问用户** | **不反问**（低置信度交给 UserCoordinator 对话处理） | 渐进确认中统一反问 |
| **输出** | WHAT + TOOL_CALL + WHY + CONFIDENCE（四字段） | 五字段（不变） |
| **LLM 温度** | Thinker 0.4 / Formatter 0.0 | 不变 |
| **最大工具调用轮数** | 默认 **3**（`analyzer_max_rounds`） | 不涉及 |

### 输入字段

```python
# Problem Analyzer Thinker 输入（与 UserCoordinator 共享上下文基底）
USER_MESSAGE: str           # 用户原始输入
CURRENT_DIALOGUE: list      # 当前对话上下文（跨轮次消息列表）
CONVERSATION_HISTORY: str   # 跨周期对话历史摘要
EXECUTION_HISTORY: str      # 跨周期执行历史摘要（TOOL_ID + 执行结果）
GATHERED_TOOLS: str         # 只读信息采集工具列表
```

`GATHERED_TOOLS` 格式为每行一个工具签名：

```
Tool_ID(param1: type = default): """param1_desc"""  # 单行简要描述
```

示例：

```
get_system_health(): """采集 CPU/内存/磁盘使用率并做阈值判断"""
get_git_status(): """当前分支、暂存区和工作区状态"""
get_git_diff(staged: bool = false): """获取未暂存或已暂存的代码改动"""
get_git_log(count: int = 10): """获取最近 N 条提交记录"""
list_top_processes(count: int = 5): """CPU/内存占用最高的 N 个进程"""
```

### 输出字段

| 字段 | 含义 | 每轮输出 |
|------|------|---------|
| `WHAT` | 已知事实 + 信息缺口 + 应补充的工具名 | 是 |
| `TOOL_CALL` | 本轮要调用的工具（支持并行，用 `\|` 分隔） | 是（最后一轮可为空） |
| `WHY` | 推断的用户意图/需求 | 是 |
| `CONFIDENCE` | 置信度：`high` / `medium` / `low` | 是 |

每次 Thinker→Formatter 调用（即每轮工具调用前后）都输出完整的四字段。CONFIDENCE 为 `high` 时，即使未达 `analyzer_max_rounds`，也可以提前终止工具调用循环。

### Thinker 推理步骤

Thinker 按以下 6 步正面引导模板推理：

```
1. 理解用户陈述
   用户的自然语言在说什么？提取字面含义。

2. 判断信息缺口
   要回答"是什么"，我还缺什么信息？基于当前已知事实和已收集数据，
   判断是否存在关键信息缺口。

3. 决策
   是否需要调用工具收集信息？
   - 简单闲聊（"你好"、"今天天气怎么样"）→ 无需工具，WHAT 写"无信息缺口"
   - 信息已充分 → 无需工具，准备归纳 WHAT
   - 存在信息缺口且未达上限 → 选择最相关的只读工具，输出 TOOL_CALL
     优先选择能覆盖更多信息维度的工具（如 get_system_health 而非逐个调
     用 CPU/内存/磁盘检查）

4. 归纳 WHAT（基于采集到的事实数据）
   - 当前系统/仓库的客观状态是什么？
   - 还存在哪些信息缺口？
   - 如果需要继续采集，应该用什么工具？

5. 推断 WHY（结合用户陈述 + WHAT 事实）
   - 用户为什么会提出这个问题？背后可能的核心需求是什么？
   - 给出一个最可能的意图推断（而非罗列所有可能性）

6. 自评 CONFIDENCE
   - high: 数据充分，意图明确，结论有把握
   - medium: 数据充分，但意图存在多种可能
   - low: 数据不足或用户输入过于模糊，无法确定意图
```

### 终止条件

分析员的工具调用循环在以下条件下终止：

| 条件 | 触发方式 | 说明 |
|------|---------|------|
| **HIGH_CONFIDENCE** | Thinker 输出 CONFIDENCE=`high` | 数据充分 + 意图明确，可提前退出 |
| **NO_TOOL_NEEDED** | Thinker 输出 TOOL_CALL 为空 | 信息充分或不需要信息收集（闲聊） |
| **MAX_ROUNDS** | 工具调用轮数达到 `analyzer_max_rounds`（默认 3） | 硬上限保护，防止上下文溢出 |

注意：**没有 NEEDS_CLARIFICATION 出口**。分析员不反问用户。当 CONFIDENCE 为 `low` 时，分析员仍然输出 WHAT（已收集到的有限事实）和 WHY（最可能的推断，但标注低置信度），交给 UserCoordinator 在渐进确认中与用户对话。保持**单一人机交互出口**（UserCoordinator）。

### 工具权限模型

`tools/tools.csv` 新增一列 `Permission`，取值：

| 值 | 含义 | 可被谁调用 |
|----|------|-----------|
| `readonly` | 只读，无副作用 | Problem Analyzer + Scheduler |
| `write` | 有写操作 | 仅 Scheduler（需 IS_EXECUTE 用户确认后） |

分析员只能调用 `Permission=readonly` 的工具。最坏情况：4B 模型幻觉导致分析员选错了工具或误读了结果 → WHAT/WHY 不准确 → UserCoordinator 可能匹配次优 SOP。但**没有写操作被执行**，用户系统状态不变。"分析错误最多导致次优匹配"的代价，远小于"跳过分析直接执行错误的 SOP"。

分析员不输入任何 SOP——只输入 `GATHERED_TOOLS`（只读工具列表），SOP 保持为操作任务执行蓝图，分析员不需要 SOP 的步骤约束。

### State 字段新增

```python
# OverallState 新增字段（TypedDict 扩展）
analyzer_what: str          # WHAT — 已知事实 + 信息缺口
analyzer_why: str           # WHY — 推断的用户意图/需求
analyzer_confidence: str    # "high" / "medium" / "low"
analyzer_tool_calls: str    # 最近一轮的 TOOL_CALL（供执行器解析）
analyzer_rounds_used: int   # 实际使用的工具调用轮数
```

### REPL 主循环变更（main.py 简化示意）

```python
# --- Problem Analyzer (新增) ---
if get_config().get("analyzer_enabled", False) and not is_command:
    analyzer_rounds = 0
    max_rounds = get_config().get("analyzer_max_rounds", 3)

    while analyzer_rounds < max_rounds:
        analyzer_result = await run_llm_node(
            "ProblemAnalyzer", problem_analyzer_fn, state,
            top_status_data, app, console
        )
        state.update(analyzer_result)

        # 提前退出：高置信度
        if state.get("analyzer_confidence") == "high":
            break

        # 提前退出：本轮不需要工具调用
        if not state.get("analyzer_tool_calls"):
            break

        # 执行工具调用（只读工具，通过 ToolDispatcher）
        tool_results = execute_tool_calls(state["analyzer_tool_calls"])
        state["execution_history"] += format_tool_results(tool_results)
        analyzer_rounds += 1

# --- UserCoordinator (增强输入) ---
# Thinker 输入中增加：
# WHAT: {state["analyzer_what"]}
# WHY: {state["analyzer_why"]}
# CONFIDENCE: {state["analyzer_confidence"]}
```

## 为什么这么做

### 人机协作的信息流向从单向变为双向

现有流程中，**模型始终是被动接收信息的一方**——用户描述 → UserCoordinator 理解 → 反问用户。对于 "系统有点卡" 这样的问题，UserCoordinator 手里只有这句话，它只能把问题抛回给用户。

问题分析员的引入改变了信息流向：**模型可以主动获取信息，而不只是被动等待用户提供。** 信息收集是 Agent 执行能力的第一步，不应该外包回给用户。

### "是什么 → 为什么 → 怎么办"是通用问题解决范式

将问题分析员和 UserCoordinator 按此范式拆分，边界清晰、各司其职：

- **WHAT + WHY**（分析员）：基于实时数据做事实归纳和意图推断，不涉及"怎么做"
- **HOW**（用户协作员）：基于分析报告做 SOP 匹配和确认，不涉及"信息从哪来"

两个节点的 prompt 各自聚焦、互不干扰。这种拆分也让 4B 模型在每个节点的推理负担更轻——分析员只管"看清问题"，协调员只管"确认执行"。

### 不推荐 SOP、不反问用户——"建议"与"决策"分离

分析员只输出 WHAT（事实）和 WHY（意图推断），不做 SOP 匹配，不推荐解决方案。这是有意为之——分析员对 SOP 库没有全局视野（它不输入 SOP），让它推荐 SOP 反而容易产生幻觉。

反问用户同理——如果分析员和 UserCoordinator 都有反问出口，用户面对两个不同的"对话者"，体验割裂。统一走 UserCoordinator 的渐进确认，保证人机交互的一致性。

### CONFIDENCE 让 UserCoordinator 的确认策略可以差异化

分析员自评置信度，让 UserCoordinator 可以区分处理：

- **high** → 快速通道：UserCoordinator 确认更简洁，减少不必要的对话轮次
- **medium** → 标准通道：展示更多上下文，让用户参与判断
- **low** → 慢速通道：UserCoordinator 知道需要主动发起澄清对话

这比原 RFC 中 UserCoordinator 对分析报告"一视同仁"要高效。同时也是分析员诚实性的体现——让 4B 模型自评"我有多确定"，不确定时不下结论，交给下游处理。

### 只读权限是零风险的信息收集

分析员只能调用 `Permission=readonly` 的工具。无论 4B 模型产生什么幻觉，**没有写操作被执行**，用户的系统状态不变。这种"分析错误最多导致次优匹配"的代价，远小于"跳过分析直接执行错误的 SOP"。

如果分析员拥有写权限，幻觉可能导致 `git commit` 在用户不知情的情况下被执行——这在安全上是不可接受的，也违背了 UserCoordinator 的 IS_EXECUTE 闸门设计。

### 设计为可选模块

`analyzer_enabled` 开关让分析员成为可选模块：

- 闲聊场景不需要信息收集，强制运行浪费 token 和延迟
- 部分用户偏好快速响应，宁可让 UserCoordinator 直接处理
- v0.2 引入新模块时，开关允许用户在遇到问题时快速回退到 v0.1 行为

### 分析报告作为 UserCoordinator 的增强输入，而非替代

分析员的输出**增强**了 UserCoordinator 的输入，而不是替代它。UserCoordinator 仍然接收 `USER_MESSAGE`、`CURRENT_DIALOGUE`、`CONVERSATION_HISTORY`、`EXECUTION_HISTORY`、`SOP_LIBRARY`，同时新增 `WHAT`、`WHY`、`CONFIDENCE`。

分析报告是"事实+推断"性质的——UserCoordinator 可以采纳分析员的意图推断，也可以根据与用户的对话上下文独立判断。**协商式而非命令式**的信息传递，保留了两层各自的专业判断空间。

## 不这么做会怎样

### 继续用当前架构处理模糊问题

用户说 "系统有点卡" → UserCoordinator 没有系统数据 → 只能输出 "你的系统可能负载较高，我建议使用 FULL_SYSTEM_HEALTH_CHECK SOP 来检查。你确认吗？"

这个回复的问题在于：
- 用户不知道自己需要确认什么（SOP 名称对用户没有意义）
- 如果系统其实不卡（只是某个应用 UI 响应慢），Agent 匹配了错误的 SOP
- 浪费了一轮对话——用户说 "是"，然后 SOP 执行，然后发现其实不是系统问题

有了分析员：自动收集 CPU/内存/磁盘/进程数据 → WHAT "Chrome 占用 4.2GB" → WHY "用户需要释放内存" → UserCoordinator 基于事实对话 → 对话质量从"盲猜"提升到"有数据支撑的建议"。

### 在 UserCoordinator 内部实现信息收集

UserCoordinator 的 Thinker 需要额外描述"在什么情况下应该建议调用工具"，Formatter 输出需要增加第六个字段（工具调用），Validator 需要增加校验规则。最致命的是，`IS_EXECUTE` 闸门只管 SOP 执行不管信息收集——框架需要新的执行路径来分发自主工具调用。

结果：UserCoordinator 变成信息收集（自主）和意图确认（人机协作）两个角色强行塞在一个节点里。Prompt 互相干扰，Formatter 输出格式脆弱性翻倍。

### 给分析员写权限

边界是模糊的。`generate_commit_message` 确实只调用 LLM，但 `git_commit` 确实会修改 Git 历史。一旦开了"有些写操作也可以"的口子，每个新工具都需要在"安全 / 不安全"的灰色地带做判断。`Permission=readonly` 是清晰的白/黑二分——没有灰色地带。

### 不做信息收集，直接让用户提供所有信息

这是 ChatGPT 的模式：用户需要自己描述清楚问题，模型才能给出有用的回答。但对于 Agent 来说，如果用户需要先 `top`、`df`、`ss` 各跑一遍再把结果贴给 Agent——那 Agent 的工具执行能力就成了摆设。信息收集是 Agent 执行能力的第一步。

### 分析员成为必选路径

如果去掉 `analyzer_enabled` 开关，每次输入都经过分析员 → 闲聊 "你好" 也走一遍分析流程 → Thinker 判断无需工具 → 浪费一次 LLM 调用（~0.5-1s 延迟 + token 消耗）。开关在"快速"和"深度"之间选择，保留 v0.1 的轻量路径。
