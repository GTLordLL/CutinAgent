# CutinAgent 解决的个人用户痛点

## 一、成本痛点：个人用户"用不起"AI Agent

### 1. 大模型 API 太贵

GPT-4、Claude 等大模型按 token 计费，单次 Agent 调用（长 prompt + 多轮工具调用循环）轻松消耗数万 token。个人开发者如果想让 AI 做日常自动化——每天检查系统状态、自动提交代码、生成工作日报——一个月的 API 费用轻松超过订阅费本身。

**CutinAgent 的做法**：全部在本地 GPU 上运行 qwen3:4b 模型（Q4_K_M 量化，显存占用约 4.2GB），零 API 调用，零订阅费。对于已经拥有 RTX 3060 的个人用户来说，硬件成本已沉没，使用成本为零。

### 2. 主流 Agent 框架硬件门槛高

AutoGPT、LangChain Agent、OpenClaw 等框架默认依赖 GPT-4 或至少 7B-13B 级别的模型，需要 RTX 4090 24GB 或云 GPU 实例。大多数个人开发者只有消费级显卡（RTX 3060 6GB 或同级）。

**CutinAgent 的做法**：专为 RTX 3060 6GB 设计。qwen3:4b 约 4B 参数，6GB 显存即可全部层上 GPU。通过架构约束（Thinker+Formatter 双阶段、专家工具内部闭环）从 4B 模型中"压榨"出可靠的 Agent 执行力，而非依赖更大模型。

---

## 二、隐私痛点：数据不想也不能上云

### 3. 云端 AI 工具要求上传本地数据

使用 ChatGPT、Claude、Copilot 等意味着把系统日志、代码 diff、服务器配置、个人文件上传到第三方云平台。对个人开发者来说，私有代码仓库、个人服务器的诊断信息、本地文件内容——这些数据一旦上传就失去了控制权。

**CutinAgent 的做法**：全本地运行。SOP 库、工具执行过程、对话记录、执行日志全部存储在本地 `history/` 目录。Ollama 容器运行在 localhost，模型下载完成后无需网络连接。物理隔离，数据不出本机。

### 4. 对比依赖云 API 的 Agent 方案

OpenClaw、Claude Code 等方案虽然强大，但：
- 所有推理在云端完成，你的代码、日志、文件内容全部流经第三方服务器
- 按 token 付费，高频使用成本不可控
- 断网即不可用

**CutinAgent 的定位**：用消费级硬件换取"数据主权"——在智能和隐私之间不做取舍，两者兼得。

## 三、可控性痛点：自主 Agent"不可信"

### 5. AutoGPT 式自主 Agent 是黑盒

传统 Agent 框架给 LLM 最大自由度——自主选择工具、自主决定执行顺序、自主判断何时停止。行为在多次运行间不可预测，出问题时无法审计"为什么 Agent 做了这个决定"。

**CutinAgent 的做法**：SOP 驱动。LLM 不是决策者，而是人类编写的 SOP 的"数字执行员"。每一步执行都追溯到 SOP Markdown 文件中的具体行。同一条 SOP，每次执行路径一致。出问题时不需逆向分析黑盒模型，直接检查 SOP 文件即可。

```
自主型 Agent：   LLM 大脑自由思考 → 自主选工具 → 结果：聪明但不可预测
CutinAgent：    SOP 文件定义步骤 → LLM 按步骤执行 → 结果：机械但可审计
```

### 6. 缺少"执行前确认"的安全闸门

多数 Agent 框架从用户意图直接跳到执行，中间没有确认环节。Agent 可能因为理解偏差执行了错误的操作，用户没有机会审查和纠正。

**CutinAgent 的做法**：UserCoordinator 实现三级渐进式确认——

1. **Stage 1（SOP 匹配）**：推荐匹配到的 SOP，请求用户确认"是这个吗？"
2. **Stage 2（行动细化）**：确认缺失的具体信息（时间范围、目标目录等），提供合理默认值
3. **Stage 3（最终确认）**：展示完整摘要（做什么 + 为什么做），等待用户输入 `y` 才真正执行

核心是 **IS_EXECUTE 闸门**——LLM 输出和实际执行之间的硬开关。在用户明确说"yes"之前，Agent 不能执行任何操作。

### 7. 工具无安全分级，误操作风险高

传统 Agent 工具集混合了读和写操作。一次幻觉的工具调用可能删除文件、破坏配置。

**CutinAgent 的做法**：
- 11 个 Linux 诊断工具全部只读命令（`ps`、`df`、`ss`、`grep` 等），无写入/删除/修改操作
- 即使 git_commit 也是可逆的（`git reset --soft HEAD~1` 即可回滚）
- 最坏情况：4B 模型幻觉导致错误诊断，而不是删除你的文件

## 四、可靠性痛点：小模型做 Agent "不稳"

### 8. 4B 模型输出格式不稳定

qwen3:4b 同样 prompt 有时输出 JSON，有时 Markdown，有时自然语言——对 Agent 流水线来说，格式错误等于系统崩溃。

**CutinAgent 的做法**：Thinker + Formatter 双阶段推理。

- **Thinker（温度 0.4）**：自由文本推理链，无格式约束。链式思考本身抑制幻觉——想得越细，编造越少。
- **Formatter（温度 0.0）**：从推理链提取关键决策，不做创造性工作。零温度保证确定性。
- **Validator**：正则/规则白名单校验（SOP_ID 是否在索引中、Tool_ID 是否在注册表中）。校验失败 → 错误信息反馈 → Formatter 重试（最多 3 次）。

实测结果：三个 LLM 节点 × Formatter **零重试，100% 格式准确率**。

### 9. "不要做 X"式的负面约束 Prompt 工程低效

不断加"不要编造工具名""不要跳过步骤"等否定约束，只会增加 prompt 长度、让 4B 模型困惑，不能从根本上解决问题。

**CutinAgent 的做法**：正面引导。告诉模型"基于已有的 SOP_LIBRARY 描述你能解决的问题"而非"不要编造不存在的 SOP 能力"。每个意图分支显式要求输出格式。Validator 做最后防线，而非第一道防线。

### 10. 小模型上下文窗口有限，多轮执行后"失忆"

4B 模型上下文窗口 8K tokens（从默认 2K 定制扩展）。多轮 Agent 执行中，SOP 计划 + 工具结果 + 对话历史很快塞满上下文。

**CutinAgent 的做法**：
- **Compactor（LLM 节点）**：每次任务完成后将对话和执行历史压缩为精简摘要，累积为跨周期的长期记忆
- **ProgressUpdater（纯代码节点）**：机械式追加进度标记到 SOP_PLAN 行尾，不消耗 LLM 上下文
- **CURRENT_DIALOGUE 生命周期管理**：仅在 Compactor 完成 + 用户满意后清除

## 五、工作流痛点：现有方案要么太死板、要么门槛太高

### 11. Dify 式拖拽工作流灵活度不够

Dify、Node-RED、n8n 等可视化工作流工具需要在 GUI 画布上画框和连线。复杂条件分支、迭代循环、变量传递在图形界面中反而变得难以理解和维护。改一个步骤意味着重新拖拽调整整个图。

**CutinAgent 的做法**：SOP 用结构化自然语言编写 Markdown 文件。Plan_Steps 支持三种控制流：

- **顺序**：`1. 调用 xxx` → `2. 调用 yyy` → `3. FINISH`
- **条件**：`如果 CPU 超过 80%，就调用 list_top_processes。否则跳过此步骤。`
- **迭代**：`基于步骤1的文件列表，为其中每一个文件调用 check_file_access`

从计算理论角度，这三种控制流构成了结构化程序定理的完备基础，足以表达任意任务逻辑。读和改一个 Markdown 文件，比在画布上拖拽直观得多——写 SOP 就像写 TODO 清单。

### 12. 想给 AI 加能力必须写代码改框架

大多数 Agent 框架扩展新能力需要：写 Python 函数 → 注册到框架 → 修改路由逻辑。不会编程的用户被排除在外。即使是开发者，为每个新任务改框架代码也是高摩擦的。

**CutinAgent 的做法**：新增能力只需三步，框架代码不动：

1. 封装专家工具（如果现有 11 个工具覆盖不了）——按四字段契约格式编写
2. 写一个 SOP Markdown 文件（`sop/NEW_TASK.md`），含 Objective、Plan_Steps、异常处理
3. 在 `sop/sops.csv` 中添加一行索引

可以用 Claude Code 等大模型辅助编写 SOP 和工具（读取 `tools.csv` 了解工具能力），但运行时仍然只依赖本地 4B 模型。

### 13. 传统脚本和语音助手不理解意图

- **语音助手（Siri、车载助手）**：本质是关键词触发器 + if-else 路由表。"帮我查一下为什么车子最近油耗变高了"——不匹配任何预设指令，直接死机。
- **Bash/Python 脚本**：处理结构化数据没问题，但模糊的自然语言输入会让它们崩溃。写脚本需要知道精确的参数格式和调用顺序。
- **传统助手是"听口令，做动作"，CutinAgent 是"给目标，看方案，去执行"**。

**CutinAgent 的做法**：LLM 做语义路由器。"帮我检查一下系统有没有异常"被解析为意图 → 匹配到 FULL_SYSTEM_HEALTH_CHECK SOP → 分解为具体工具调用和参数。LLM 在人类自然语言和机器操作之间架起了桥梁。

## 六、当前实际能力与限制

### CutinAgent 现在能做什么

**已部署 SOP（开箱即用）**：
| SOP | 功能 |
|-----|------|
| GIT_SMART_COMMIT | 扫描工作区变更 → LLM 分析 diff → 生成 Conventional Commits 格式的 commit message → 暂存并提交 |
| GIT_BRANCH_CLEANUP | 扫描本地分支列表 → 识别已合并过期分支 → 安全删除 |
| GIT_PR_CREATE | 分析当前分支变更 → 生成 PR 描述 → 推送并创建 GitHub Pull Request |

**草稿 SOP（sop/draft/，已设计待完善）**：
| SOP | 功能 |
|-----|------|
| FULL_SYSTEM_HEALTH_CHECK | 全面系统健康检查（CPU/内存/磁盘/时钟/异常进程），含条件跳转和报告生成 |
| SERVICE_DIAGNOSTIC | systemd 服务故障诊断，含 INTERRUPT 等待人工判断 |
| DISK_CLEANUP_SCAN | 扫描大文件，检查访问权限，生成清理清单 |
| QUICK_PORT_CHECK | TCP 端口监听状态检查 |
| NETWORK_CONNECTIVITY_TEST | ping + HTTP 连通性测试 |

**可用工具集（11 个）**：
- 5 个 Git 工具：get_git_status, get_git_diff, get_git_log, git_commit, generate_commit_message
- 10 个 Linux 诊断工具（只读）：get_system_health, list_top_processes, check_network_port, test_connection, locate_large_files, get_service_status, grep_log_content, read_env_vars, check_file_access, check_system_sync
- 1 个 LLM 报告生成器：generate_summary_report

### 诚实披露：当前限制

| 限制 | 说明 |
|------|------|
| **单轮推理 ~15-25 秒** | 每次 LLM 调用约 12-25 秒，完整任务通常 2-3 分钟。不适用于实时或紧迫场景 |
| **SOP 步骤上限 ~6 步** | 超过 6 步时 4B 模型可能产生幻觉（遗漏或合并步骤）。这是模型限制，不是架构限制 |
| **写 SOP 有学习曲线** | 需要理解工具集的能力边界和参数约束。可借助 Claude Code 等大模型辅助编写 |
| **工具集有限** | 当前覆盖 Git 操作 + Linux 诊断。面对新领域需封装新的专家工具 |

### 三个同时满足的稀缺属性

大多数 AI 产品在以下三个维度上是"三选二"：

| 产品类型 | 可编程 & 可扩展 | 低成本 | 数据不出本地 |
|---------|:---:|:---:|:---:|
| GPT-4 API 应用 | ✅ | ❌ 贵 | ❌ 数据上传 |
| Home Assistant 等 | ❌ 硬编码 | ✅ | ✅ |
| 开源 Agent 框架 | ✅ | ❌ 需大模型 | ✅ |
| Dify / n8n | ✅ 拖拽工作流 | ❌ 依赖云 API | ❌ |
| **CutinAgent** | ✅ SOP 自然语言 | ✅ 4B/6GB 可跑 | ✅ 全本地 |

**三个同时满足的，市面上几乎没有。**
